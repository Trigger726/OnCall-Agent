## 3. 设计取舍与成熟产品参考

### 3.1 为什么先做复盘闭环，而不是立刻接 Kafka

V1.4/V1.5 已经把单实例事件持久化、游标回放、取消、超时和饱和反馈做实；V1.6 的剩余真实历史样本和备份销毁又依赖外部数据/制度。复盘是路线图中可在当前仓库形成真实业务闭环的下一能力，也比“为了技术名词先引入消息队列”更容易证明校招项目价值：它同时覆盖领域建模、治理门禁、职责分离、并发控制、审计和 UI。

### 3.2 参考依据

[Google SRE Postmortem Culture](https://sre.google/sre-book/postmortem-culture/) 将影响、行动、根因、后续工作、无责文化和正式评审视为高质量复盘的重要组成。[FireHydrant Conducting Retrospectives](https://docs.firehydrant.com/docs/conducting-retrospectives) 强调从 Incident 汇集时间线和事件证据，并在事故后形成复盘；其 [Managing Follow-ups](https://docs.firehydrant.com/docs/managing-follow-ups) 把事故后的整改项与事中任务区分并持续跟踪。OpsPilot 借鉴这些业务原则，但使用当前模块化单体、角色和审计模型实现，不宣称具备这些成熟平台的全部集成与规模能力。

### 3.3 快照、正文与行动项的边界

- 快照保存“创建复盘时系统已经知道的事实”，创建后不随时间线追加而漂移；
- 正文保存人的分析，草稿可修改，发布后冻结；
- 行动项保存未来要验证的防复发工作，发布后仍需继续完成；
- 完成行动项不反向改写已发布复盘版本，而是在时间线和审计中追加事实。

## 6. 诚实边界与下一步

1. 当前行动项只在 OpsPilot 内跟踪，尚未同步 Jira/飞书/企业微信等外部工单系统。
2. 截止日期有创建校验，但还没有到期提醒、升级策略和逾期指标。
3. 当前复盘一 Incident 一份、发布后正文冻结；尚未实现修订版/勘误流程。
4. 还没有跨 Incident 相似性聚类、重复事故率、MTTA/MTTR 和 Runbook 命中率看板。
5. 自动草稿基于结构化规则，不冒充模型能自动判断真实根因；后续即使引入模型，也必须保留证据引用和人工复核门禁。
6. 下一检查点优先实现可复现的复盘指标与行动项逾期视图，再评估 OpenTelemetry 或多实例事件分发；不会只为简历关键词堆基础设施。
