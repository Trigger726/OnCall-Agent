# V1.6 检查点 02：持久化向量索引、RRF 与可解释降级

日期：2026-09-02

结论：部分通过。版本绑定的向量索引、内容指纹幂等、原子替换、BM25/向量 RRF、显式降级、按引擎评测、H2 自动化和桌面/移动端实页验收已闭环；本机没有可用的 Docker 引擎和真实 DashScope 凭证，因此本轮没有取得 MySQL 8.4 Flyway V8 或真实 Embedding 质量证据，不能标记最终通过。

## 原始 OnCall 基线审计

通过 Git index 只读检查保留的原始源码，没有恢复或覆盖当前工作树。原链路为：

```text
DashScope text-embedding-v4
  -> Milvus L2 search
  -> optional gte-rerank
  -> RAG answer
```

保留的价值是语义召回和 rerank 思路；本轮没有照搬以下工程缺口：

- 应用启动硬依赖 API Key/Milvus，外部服务不可用时不能维持核心流程。
- 向量索引按文件路径管理，没有绑定不可变 Runbook 版本、chunk 内容哈希和业务 ACL。
- L2 距离被直接称为 score，缺少与 BM25 的量纲边界和稳定融合策略。
- rerank 失败直接中断，不提供可观察降级。
- 没有固定标注集，无法证明语义链路相对关键词方案的收益。

原始源码仍由 Git 历史/index 保留；V1 的 3 条内置 `runbook` 数据仍在新应用中作为 `LEGACY_CONTAINS_V1` 基线，满足历史 Demo 与新 Demo 可独立对照的要求。

## 本轮交付

- Flyway V8 新增 `runbook_chunk_embedding`：向量绑定 `chunkId + provider + model + contentHash + dimensions`；新增 `runbook_embedding_index_run` 保存 `RUNNING / COMPLETED / FAILED`、语料指纹、分块数、维度和操作者。
- 索引构建先在事务外批量调用 Spring AI `EmbeddingModel`，校验返回数量、统一维度、有限值与非零范数；全部成功后在短事务中原子替换当前 `provider + model` 索引。
- 当前已发布语料、provider 与 model 生成稳定 SHA-256 指纹；指纹及分块数未变化时直接复用上次成功运行。Provider 失败只记录错误码，旧向量不会先被删除。
- 查询严格先做文档角色 ACL，再运行 BM25；完整向量索引可用时追加余弦排名，并以 RRF `Σ 1/(60+rank)` 融合。响应返回请求模式、实际引擎、词法/向量名次、语义原始分、覆盖率和 warning。
- `AUTO / BM25 / HYBRID` 支持显式对照；索引关闭、Provider 缺失、覆盖不足或查询失败时均回退 `BM25_LOCAL_V1`。显式选择 HYBRID 时页面提示“HYBRID 请求未执行；已降级 BM25”，不会把请求意图当成实际执行结果。
- 固定种子集从 3 条扩充到 13 条，覆盖 Redis、接口延迟、认证、Kafka、MySQL 和 Kubernetes；每次评测分别保存 contains、BM25、Hybrid 的指标/失败列表，Hybrid 不可用时保存 unavailable 原因而不是复制 BM25 数字。
- 页面新增四栏新旧对照、语义索引状态、`AUTO / BM25 / HYBRID` 模式切换、实际执行引擎、双路名次与降级说明；管理员/运维经理在启用真实 Provider 后可幂等重建索引。

## 设计依据

- [Elastic Hybrid Search](https://www.elastic.co/docs/solutions/search/hybrid-search/) 推荐以 RRF 组合 lexical 与 vector search。
- [Elastic RRF API](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion) 给出 `rank_constant` 与排名融合定义，默认值为 60。
- [Milvus Hybrid Search Retriever](https://milvus.io/docs/milvus_hybrid_search_retriever.md) 同样采用 dense/sparse 多路召回与 RRF。
- [Milvus Contextual Retrieval](https://milvus.io/docs/contextual_retrieval_with_milvus.md) 用固定查询集和 Pass@K 对比不同检索配置，支持“先评测再决定是否进入主链路”的路线。

当前语料只有个位数分块，因此本轮用数据库持久化 JSON 向量和内存余弦验证业务与可靠性契约，没有为了简历名词堆砌重新引入 Milvus。未来替换 ANN/OpenSearch/Milvus 时，上层 ACL、RRF、降级和评测契约保持不变。

## MySQL 与外部 Provider 边界

`MySqlCompatibilityIntegrationTest` 已更新为断言 Flyway V8、6 份已发布文档和空的默认向量表。宿主机 `docker info` 当前仍无法连接 `dockerDesktopLinuxEngine`，因此本轮未实际启动 MySQL 8.4；没有把 H2 MySQL 模式当成真实 MySQL 证据。

本轮也未配置或传输真实 DashScope Key。代码已通过 Spring AI `EmbeddingModel` 接口接入 `text-embedding-v4`，但只有受控测试替身证据；真实模型的 Recall/MRR、延迟、限流、费用和中文领域效果均待测。

恢复条件后的命令：

```powershell
.\mvnw.cmd -Dopspilot.mysql.it.enabled=true '-Dtest=MySqlCompatibilityIntegrationTest' test

$env:RUNBOOK_SEMANTIC_ENABLED='true'
$env:DASHSCOPE_API_KEY='<local-secret>'
.\mvnw.cmd spring-boot:run
```

## 已知边界与下一步

- 13 条是种子集，不是从历史 Incident 或检索日志形成的真实人工标注；下一步先建立来源、标注人、难度和时间切分，而不是继续添加“容易命中”的样例。
- 当前向量查询从数据库加载 JSON 后做内存全量余弦，只适合小语料；需要基于规模和延迟证据再选择 ANN/OpenSearch/Milvus。
- RRF 是召回融合，不是 cross-encoder rerank；仅在真实标注集证明稳定增益后接入 `gte-rerank`，并要求失败回退 RRF。
- 真实 Provider 尚缺超时/限流/费用观测与契约测试；不能只依赖 SDK 默认行为。
- MySQL V7/V8、容器镜像和启用真实 Embedding 的运行路径仍需补验，因此检查点保持“部分通过”。
