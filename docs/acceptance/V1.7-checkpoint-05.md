## 2. 风险与设计

checkpoint 04 已确认 H2 双线程只创建一个 Problem，但 MySQL 用例当时只顺序执行。`ProblemService.create` 的旧路径先普通查询、再插入；唯一键冲突后仍用普通查询回读。依据 [MySQL 8.4 一致性非锁定读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)，REPEATABLE READ 的普通读取使用事务内既有快照，存在继续看不到另一事务刚提交行的风险。

本轮将冲突后的回收改为 `SELECT ... FOR UPDATE`。这是当前读，只作用于已经发生唯一键竞争的慢路径；无竞争请求仍保留原普通查询，不扩大锁范围。数据库唯一约束继续承担最终一致性，代码不引入 JVM 本地锁，因此多实例部署语义不变。

## 3. 确定性测试

真实 MySQL 条件测试新增第二个独立用例：

1. 在已提交数据中准备同服务、同指纹、跨两个 Incident 的候选。
2. 启动两个显式 REPEATABLE READ 事务，各自先查询并断言 Problem 不存在，从而确定性建立旧快照。
3. 两个事务到达闸门后同时调用真实 `ProblemService.create`，所有屏障和 Future 均设置等待上限。
4. 要求结果恰好一次创建、一次复用，两个响应返回同一 Problem；新关联数为 2 和 0。
5. 提交后按复发键、Problem 主键和时间线证据引用查询，要求一条 Problem、两条关联、两条 `PROBLEM_LINKED` 时间线。

测试类固定先运行既有 MySQL 全链路，再运行并发用例，避免共享容器中的全局空表断言受反射顺序影响。该顺序本身不是并发正确性的来源；并发用例仍使用两个独立事务和线程。
