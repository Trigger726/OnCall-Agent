# V1.7 checkpoint-42：未确认 Incident 的值班升级执行

日期：2026-09-25；2026-09-27 续验。状态：UTC 时钟混用已修复，本地 UTC/上海时区全量与 JAR 打包通过；首轮 MySQL 已通过，修复后的远端门禁待补证。

## 问题与设计

旧值班页展示静态升级策略，却没有执行器。新 Incident 仅在创建时尝试写一条 `notification_log`，到期后不检查确认状态，也不会执行 USER/ROLE 后续步骤；过期的种子班次使“当前值班人”经常为空。与成熟 Incident 路由中“接入→分组→升级直到确认”的流程相比，这不能支撑真实未确认事故运营。参考 [Grafana IRM 路由与升级流程](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/introduction/routing-and-escalation/)；这里只实现站内路由记录，不声称短信、电话或外部送达。

V24 给策略增加严重度筛选，并为每个 Incident/步骤建立唯一的升级事件。新 P1 Incident 创建后立即执行到期的零分钟步骤；定时扫描每分钟检查仍为 `OPEN` 的事故，按策略时限执行后续步骤。扫描先锁定 Incident，再复核状态与已有事件；并发扫描仅保留一份事件、时间线、审计和站内通知记录。重叠班次按临时覆盖、开始时间和 ID 排序，只选活跃用户；USER 与 ROLE 也只路由活跃账号。没有有效目标时记录 `NO_TARGET`，不生成假通知。确认后停止；迟到扫描会补执行所有已到期且未执行的步骤，单次最多处理 100 个候选 Incident。

## UTC 失败与时钟修复（2026-09-27）

本机以 `-Duser.timezone=UTC` 复现全量失败：`ProblemManagementIntegrationTest` 原本应聚合到 Incident 203，却新建了 204。原因是本检查点将创建与聚合窗口改为硬编码上海应用时间，但既有数据库时间、确认与恢复仍使用 `CURRENT_TIMESTAMP`；UTC 环境产生八小时错位，且存在确认时间早于创建时间的风险。

修复统一使用数据库会话时钟：创建时间保留表默认值，聚合窗口在 SQL 中计算，当前班次与默认升级扫描也使用数据库时间。没有更改 Problem Management 的旧断言，也没有迁移/覆盖历史数据；逐条时区信息及多时区排班仍不在本检查点范围。新增告警回归通过真实状态转换接口确认事故，检查创建时间接近数据库时钟、确认不早于创建、确认后不继续升级。UTC 定向执行升级 5 项与 Problem Management 3 项全部通过。CI 增加 UTC 打包与上海时区全量回归两步，继续验证环境差异。

续验命令 `mvnw -Duser.timezone=UTC package -q` 与 `mvnw -Duser.timezone=Asia/Shanghai test -q` 均退出 0；每轮发现 125 项、执行 110 项、0 失败/错误、15 项 Docker 条件跳过。UTC 命令同时完成可执行 JAR 打包；本次没有修改前端，页面证据仍为 09-25 的实际验收，不冒充重新浏览器验收。
