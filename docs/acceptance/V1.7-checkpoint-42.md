# V1.7 checkpoint-42：未确认 Incident 的值班升级执行

日期：2026-09-25。状态：本地通过；H2 全量、前端测试/构建、真实 JAR/API 及桌面/390px 页面已通过，MySQL 和远端容器门禁待补证。

## 问题与设计

旧值班页展示静态升级策略，却没有执行器。新 Incident 仅在创建时尝试写一条 `notification_log`，到期后不检查确认状态，也不会执行 USER/ROLE 后续步骤；过期的种子班次使“当前值班人”经常为空。与成熟 Incident 路由中“接入→分组→升级直到确认”的流程相比，这不能支撑真实未确认事故运营。参考 [Grafana IRM 路由与升级流程](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/introduction/routing-and-escalation/)；这里只实现站内路由记录，不声称短信、电话或外部送达。

V24 给策略增加严重度筛选，并为每个 Incident/步骤建立唯一的升级事件。新 P1 Incident 创建后立即执行到期的零分钟步骤；定时扫描每分钟检查仍为 `OPEN` 的事故，按策略时限执行后续步骤。扫描先锁定 Incident，再复核状态与已有事件；并发扫描仅保留一份事件、时间线、审计和站内通知记录。重叠班次按临时覆盖、开始时间和 ID 排序，只选活跃用户；USER 与 ROLE 也只路由活跃账号。没有有效目标时记录 `NO_TARGET`，不生成假通知。确认后停止；迟到扫描会补执行所有已到期且未执行的步骤，单次最多处理 100 个候选 Incident。
