## 缺陷与设计依据

基线 `1157e4f` 的 AgentEventReceiver 只按内存游标 XREAD。根据 [Redis XREAD](https://redis.io/docs/latest/commands/xread/) 的严格大于游标语义，若 Stream 被重建且 ID 小于或等于旧游标，保留原接收器的情况下可能一直空读。业务 SSE 仍有数据库兜底，但不能把兜底可用等同于通知通道已恢复。

先新增 8 项单元场景，旧生产代码失败 6 项，均缺少第二条通知；[修复前失败摘要](assets/V1.7-checkpoint-17/receiver-before-fix.txt) 已保留。修复后相同 8 项通过，覆盖毫秒/序号回退、超过有符号 long 上限的合法 Redis ID、同 ID 不同字段、观察到空 Stream、尾记录未变及检查异常。

## 实现与边界

- 仅在 XREAD 空读且当前游标非 `0-0` 时执行 [XREVRANGE](https://redis.io/docs/latest/commands/xrevrange/) COUNT 1，最多检查一条尾通知；正常有数据读取不增加尾检查。
- 尾部为空、尾 ID 数值小于游标，或尾 ID 相同但字段被替换时，将**传输游标**重置为 `0-0`，下一次调度开始重读。ID 按两段无符号 64 位数比较，不按字符串或有符号 long 排序。
- 保留每轮 COUNT 100。不在检测轮循环全量回放，不修改数据库事件、outbox 或浏览器游标。重复通知依然由已有数据库有序补读消化。
- 查询异常或无可用响应不触发重置。普通尾记录未变时不重复回放。删除尾记录也可能引起保守回读，属于允许的重复提示。
- 这是可观测尾部变化的恢复，不是 Stream 世代协议：重建后尾部已超过旧游标、或相同 ID/字段碰巧复用时，不能据此识别所有历史缺口。已丢失/裁剪的提示仍靠数据库补读，不能关闭兜底，也不能声称 Redis 数据恢复或 exactly-once。

## 真实 Redis 验证设计

RedisRelayIntegrationTest 新增两个使用独立随机测试 key 的场景，沿用真实 Redis 7.4 Testcontainers。测试只删除自己创建的 key，不操作用户 Redis。

1. 同一个 receiver 对象先接收 `100-10`，删除/重建为 `100-9`，再删除/复用 `100-9` 携带不同 eventId，最后观察 key 消失并重建为 `1-0`。必须依次收到 eventId 1、2、3、4，无重启、无数据库兜底。
2. 旧游标 `1000-0` 后重建 205 条较低 ID，检测轮不发布，后续三轮分别发布 100、100、5 条。裁剪到仅保留尾记录后空读两轮不能重放；新追加第 206 条仍可收到。
