# V1.7 checkpoint-20：执行实例崩溃后的持久化 deadline 结算

实施日期：2026-09-16。当前状态：代码、H2 集成测试与本地 JAR 已通过；真实 MySQL 并发协调与 MySQL/Redis 双 JVM 强制退出验收待本提交的 GitHub Actions 闭环。

## 原始缺口

checkpoint-09 至 19 已让 Agent 事件具备同事务 outbox、Redis Streams 通知、数据库补读、GET SSE 和前端游标恢复。但这只解决“其他实例如何看到已提交事件”，没有解决“正在执行的 JVM 被杀后，`RUNNING` 由谁收敛”。原看门狗和 `FutureTask` 只存在于执行实例内存，该实例退出后，run 可能长期留在 `QUEUED / RUNNING`。

## 实现边界

- 新增默认启用的 `AgentRunRecoveryJob`，以有界批次扫描已超过持久化 `deadline_at` 且仍处于活动状态的 run。
- 每个候选 run 在独立短事务内用 `SELECT ... FOR UPDATE` 锁定并再次检查状态与 deadline；多实例同时扫到时只有一个实例结算。
- 正常超时结算为 `TIMED_OUT`；如果持久化状态已记录取消请求，则结算为 `CANCELLED`。终态事件、Incident 时间线和系统审计在同一事务中写入。
- 运行中工具晚返回时，编排器在持久化步骤前再检查终止状态；恢复协调器已结算后，原线程不再写入成功步骤或重复终态事件。
- 该设计不自动重放六个工具，不声称 exactly-once 执行，也不是 Temporal 式的工作流续跑。它只保证 deadline 后的有界、可审计终态收敛。

设计参考 [Kubernetes Job](https://kubernetes.io/docs/concepts/workloads/controllers/job/) 的控制器调和与绝对截止时间思路，同时用 [Temporal 文档](https://docs.temporal.io/) 作能力边界对照：OpsPilot 本检查点没有实现崩溃后从中间步骤续跑。

## 未声称的能力

- 不实时感知 JVM 宕机；最晚在已持久化 deadline 到达后开始结算。
- 不自动迁移、恢复或重放已中断的工具链。
- 当前没有执行租约或 fencing token；安全性依赖工具只读和结果持久化前的终止检查。若未来允许生产写操作，必须先引入带 fencing 的执行权协调。
