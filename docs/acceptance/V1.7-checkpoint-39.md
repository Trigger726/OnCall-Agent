# V1.7 checkpoint-39：草稿行动项的发布门禁

日期：2026-09-25。状态：部分通过；本地 H2 全量回归与 JAR 打包通过，真实 MySQL 8.4 和远端 CI 待验证。

## 问题与修复

checkpoint-38 已让全局运营列表排除未发布复盘，却没有将同一门禁加到后台逾期扫描、行动项完成和通知投递。原实现可将 `DRAFT` 下已过期的行动项写入升级与通知 outbox，进而把尚未独立复核的标题、事故编号和负责人送到外部 webhook；负责人也可以在发布前完成草稿行动项。这和“独立发布后才成为正式防复发承诺”的业务语义冲突。

- 逾期扫描只选择已发布复盘的开放行动项；草稿在原 Incident 详情中仍可编辑，但不产生升级事实、时间线或通知入队。
- 完成接口对未发布复盘返回 409 `POSTMORTEM_NOT_PUBLISHED`；发布后沿用原有负责人/管理角色、版本、时间线与审计契约。
- 派发器在 HTTP 请求前复查父复盘及行动项状态。历史遗留的草稿通知标为 `FAILED / POSTMORTEM_NOT_PUBLISHED`，不向外发送；人工重试也要求已发布、开放且升级仍开放。发布后可受控重试，保留原 outbox 和幂等键，不伪造已送达。

这一门禁借鉴 [PagerDuty 对复盘行动项的负责人、日期及可追踪工作的要求](https://postmortems.pagerduty.com/culture/accountability/) 和 [Atlassian 的复盘行动项治理](https://www.atlassian.com/incident-management/postmortem/)；具体“发布后生效”是 OpsPilot 自身的治理规则，并非照搬这些项目的状态机或期限。
