## 2. 本阶段交付范围

### 2.1 可恢复的 Agent 调查事件流

- 新增 `agent_investigation_event` 持久化事件表，以数据库事件 ID 作为 SSE 游标。
- 调查过程会记录运行启动、计划、工具调用、证据采集、重规划、行动建议、完成或失败等事件。
- 新增 `POST /api/v1/incidents/{id}/investigations/stream`，通过 SSE 推送真实调查进度。
- 新增 `GET /api/v1/agent-runs/{runId}/events?after={eventId}`，支持断线后的游标回放。
- SSE 客户端断开只停止推送，不取消后台调查任务，保证调查结果和审计记录能够完整落库。
- 调查线程池采用有界队列，避免无界创建线程造成资源耗尽。

### 2.2 高风险处置的人机协同审批

- 新增 `remediation_proposal`，保存处置动作、目标资源、风险、证据、请求人与审批状态。
- 高置信度且存在变更证据的调查结果会生成 `PENDING_APPROVAL` 回滚建议。
- 新增事故维度处置建议查询和审批接口。
- 审批仅允许 `ADMIN` 或 `OPS_MANAGER`，服务端强制禁止申请人自批。
- 审批使用版本号进行乐观并发控制，过期版本返回冲突。
- 审批结果写入事故时间线与审计日志。
- 当前版本明确只完成治理审批，不直接操作生产环境。

### 2.3 前端闭环

- 事故详情页和 OnCall 助手共用真实 SSE 客户端，不再用前端伪进度表达 Agent 调查。
- 两个入口均显示实时执行轨迹和证据采集状态。
- 事故详情页展示处置建议、风险、证据、申请人和审批状态。
- 管理员或运维经理可批准或拒绝；界面会处理自批限制和版本冲突后的刷新。
- 页面卸载时仅终止客户端读取，不会取消服务端调查。

## 5. 待验项目

1. 使用本地运行服务发起真实 HTTP SSE 请求，核对事件顺序、事件 ID 和 `runId`。
2. 用 SSE 返回的游标调用事件回放 API，验证数据库状态与网络输出一致。
3. 使用 OnCall 账号发起建议，再由独立运维经理账号完成审批，核对时间线和审计记录。
4. 在桌面端和移动端检查事故详情页、OnCall 助手、实时轨迹和审批表单。
5. 更新 README、架构、演示和面试说明，使文档与 V1.4 当前能力一致。

## 6. 已知限制与风险

- SSE 事件已经持久化，但还没有跨节点消息总线；多实例部署时需要增加 Redis Streams、Kafka 或数据库轮询协调机制。
- 后台调查会在客户端断开后继续执行，但当前没有用户主动取消运行的 API。
- 处置审批只形成治理闭环，尚未接入 Argo CD、Ansible、Kubernetes 或云厂商执行器；这是有意保留的生产安全边界。
- 审批规则目前固定为单人独立审批，后续可按风险等级扩展为策略化多级审批。
