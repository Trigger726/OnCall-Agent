## 为什么不是再造一个单告警接口

[Alertmanager 官方通知数据结构](https://github.com/prometheus/alertmanager/blob/main/docs/notifications.md) 以分组 webhook 投递 `receiver`、公共标签和多条 alert；每条 alert 包含 `status`、labels、annotations、`startsAt`、`endsAt`、`generatorURL` 和 fingerprint。其职责本身就是去重、分组和路由，通用 webhook 仍采用至少一次投递语义。因此 OpsPilot 需要直接接收该批量结构，并把网络重试与真实告警状态变化区分开，而不是要求上游改造成项目私有 JSON。

## 实现与语义

- 新增 `POST /api/v1/integrations/alertmanager/webhook`，兼容 Alertmanager v4 webhook 的核心字段；单批默认最多 100 条，可通过 `ALERTMANAGER_WEBHOOK_MAX_ALERTS` 调整到 1–1000。
- 默认关闭。只有配置 `ALERTMANAGER_WEBHOOK_SECRET` 后才启用，并要求 `Authorization: OpsPilot <secret>`；比较采用常量时间，专用凭证不进入 JWT 解析。
- 资源由 `labels.resource_code` 或 `labels.service_code` 映射；严重度只接受 P1–P4、critical、warning、info，未知值明确拒绝，不静默猜测。
- 外部事件 ID 由 `fingerprint + startsAt epoch millis` 构成。同一轮告警的 firing/resolved 共用一个 ID，新一轮 firing 因开始时间不同得到新 ID。多 Alertmanager 集群应在规则标签中携带稳定 cluster 标签，使官方 fingerprint 自然区分来源。
- 相同外部 ID 且状态相同返回 `REPLAYED`，不修改 occurrence、version 或时间线；firing → resolved 返回 `UPDATED`，更新最后发生时间但不把恢复误计为新一次告警，并只追加一次 `ALERT_RESOLVED` 时间线。
- 批内永久业务错误按 item 返回 `REJECTED`，不阻断有效 alert；非预期基础设施异常仍让整个请求失败，以便 Alertmanager 重试。此前已经写入的 item 可由幂等键安全重放。
- 空批次、超批次、无效 JSON、未配置密钥和错误凭证分别返回稳定错误码；被拒 item 仅记录 index/error code，不把 labels、annotations 或凭证写入日志。

## 可证伪验收

1. 未配置密钥返回 503，错误或缺少凭证返回 401；非法 JSON 返回 400，超过上限返回 413。
2. 一批两条 alert 中，一条资源存在、一条不存在：有效项必须 `CREATED` 并创建 Incident，无效项必须 `REJECTED/RESOURCE_NOT_FOUND`，数据库中不能出现坏记录。
3. 同一 firing 连续投递两次必须得到 `CREATED / REPLAYED`；随后 resolved 连投两次必须得到 `UPDATED / REPLAYED`。
4. 上述四次投递后只有一条 alert，`occurrence_count=1`、`version=1`，并且只有一条恢复时间线。
5. 未映射的 severity 必须被拒绝，不能默认落成某个优先级。

- `AlertmanagerWebhookIntegrationTest` 3 项和禁用态测试 1 项通过，覆盖鉴权、JSON、批量上限、严重度、部分失败、重放和恢复。

- 真实 JAR 在 9900 端口健康启动；相同 webhook 的 firing、重复 firing、resolved 实际依次返回 `CREATED / REPLAYED / UPDATED`。
- 真实浏览器告警页显示 `alertmanager`、P1、已恢复、`×1` 和 Incident 链接；RESOLVED 筛选后仅保留恢复项，进入 Incident 后可见“外部告警已恢复”时间线；浏览器控制台无 warning/error。
- 本轮是入站 Alertmanager receiver，不是 OpsPilot 把 SLO 判定发送到 Alertmanager，也没有证明外部通知渠道已送达。
- Alertmanager 不会依据 200 响应体自动处置单条 rejected item；当前以结构化响应和服务端告警日志暴露，生产仍应接日志告警，后续可增加持久化拒绝台账/死信重放。
- 尚未进行大批量压测、真实 Alertmanager 容器联调和多集群碰撞验证；远端 MySQL/容器门禁以本次 GitHub Actions 结果为准。
