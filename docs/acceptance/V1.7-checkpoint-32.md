# V1.7 checkpoint-32：真实 Alertmanager 入站链路

日期：2026-09-23。状态：进行中。真实容器联调脚本、隔离配置与 CI 门禁已加入；远端实测待验。

## 目标与协议依据

前几轮以 MockMvc 和真实 HTTP 客户端构造 v4 webhook，已覆盖服务端映射、幂等、拒绝和重放，但仍未证明 Alertmanager 本身会按配置送出可被 OpsPilot 接受的请求。本轮使用固定版本 `prom/alertmanager:v0.34.1`，配置 webhook receiver、`send_resolved` 和 `Authorization: OpsPilot <secret>`；脚本只向 Alertmanager 的 Alerts API v2 投递，不直接向 OpsPilot 投递成功告警。[Alertmanager 官方配置](https://prometheus.io/docs/alerting/latest/configuration/)定义了 v4 webhook、HTTP 客户端鉴权和 resolved 通知；[官方 Alerts API](https://prometheus.io/docs/alerting/0.34/alerts_api/)允许测试工具通过 API v2 注入告警，但也明确生产应优先由 Prometheus 告警规则发送。因此本轮证明真实 receiver 链路，不冒充 Prometheus 规则到 Alertmanager 的全链路验收。

## 可证伪验收

1. 无专用鉴权直达 OpsPilot webhook 必须 401；真实 Alertmanager 携带配置的鉴权后能成功投递。
2. firing 进入 OpsPilot 后形成一条 Alert；同标签 resolved 更新同一 Alert，不增加 occurrence，并仅追加一条恢复时间线。
3. 同一 Alertmanager 分组内的合法/非法两项均被送出：合法项创建 Alert，未知 CMDB 资源进入 `OPEN` 拒绝台账；伪敏感字段在快照中被脱敏。
4. 验证使用独立 Compose project/volume，测试密钥运行时生成且不提交；脚本退出清理测试资源并保存无密钥的诊断证据。
