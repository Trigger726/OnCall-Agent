# V1.7 checkpoint-26：按服务拆分事故响应指标

日期：2026-09-19。状态：待最终 CI 复核。

## 问题与范围

原运营分析只有窗口整体的 Incident 数、MTTA/MTTM/MTTR 和严重等级分布。多个服务混在一起时，整体均值无法告诉值班经理哪个归属服务积压未关闭事故，或哪个服务的有效响应样本偏慢。本检查点在同一日期/等级窗口内增加按 `incident.service_resource_id` 分组的视图；不改动历史数据与原演示。

## 实现

- `GET /api/v1/analytics/incidents` 的 `services` 按 Incident 数降序、服务编码升序输出，包含服务 ID、编码和名称、窗口内 Incident 数、当前未关闭数以及各自 MTTA/MTTM/MTTR 的平均、中位、有效样本数。
- `RESOLVED`、`CLOSED` 不计为未关闭；`OPEN`、`INVESTIGATING`、`MITIGATED` 等其他状态仍计入。缺失或早于创建时间的里程碑不进入时长分母，且不会被填为 0。
- 前端新增服务表格与空状态，展示平均分钟数及 `n`，说明其是事故响应里程碑统计，而非可用性 SLO。行动项汇总仍是全局汇总，不随事故窗口筛选。

## 可证伪验收

1. 同窗口两个结算 Incident、一个认证 Incident：服务表显示结算 `2`、认证 `1`，结算未关闭 `1`、认证 `0`，排序确定。
2. 结算其中一个 Incident 没有确认/恢复里程碑：MTTA 和 MTTR 的分母均只能是 `1`，分别为 `5`、`30` 分钟；不能按两个 Incident 取平均。
3. 历史全局指标及日期/等级校验回归仍通过；前端构建和既有流式调查测试通过。
4. 全量后端与远端 CI 通过后，才将本检查点标记为“通过”。
