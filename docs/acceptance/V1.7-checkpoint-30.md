# V1.7 checkpoint-30：Alertmanager 拒绝台账与受控重放

日期：2026-09-23。状态：部分通过。本地 H2、后端全量、前端、JAR、真实 HTTP 和浏览器闭环已通过；真实 MySQL 8.4 与远端七项 CI 待本轮推送后复验。

## 为什么需要持久化拒绝台账

checkpoint-29 已能在 HTTP 200 中逐项返回 `REJECTED`，但 Alertmanager 不会根据响应体自动修复某一条永久坏项。如果只靠日志，值班人需要手工找回原投递，还可能重复创建告警。[GitHub Webhook 最佳实践](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)强调稳定 delivery ID 和可重投递；其[重投递文档](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks)也将重放限制为管理员操作。本检查点把这个运维闭环落到 OpsPilot，但不允许在平台内编辑原始证据：先修上游规则或 CMDB，再重放脱敏快照。

## 实现与语义

- Flyway V20 新增 `alert_ingest_rejection`，保存来源、稳定拒绝键、脱敏快照、错误、投递/重放次数、租约、解决结果和操作人。
- 优先以 `fingerprint + startsAt + status` 生成拒绝键；firing 通知中不断变化的 `endsAt` 不会制造新坏项。相同坏项重复投递只增加 `delivery_count`，原始脱敏快照保持稳定。
- labels、annotations、receiver、group key、generator URL 和 fingerprint 入库前统一经过 `LogRedactor`；列表 API 只返回结构化摘要，不暴露 `payload_json`。
- `GET /api/v1/integrations/alertmanager/rejections` 允许 ADMIN、OPS_MANAGER、ON_CALL 和 AUDITOR 查看；`POST /{id}/replay` 只允许前三类操作角色，AUDITOR 为只读。
- 重放复用原 Alertmanager mapper 和 `AlertService.intake`，不开第二套宽松校验。成功/失败写审计；成功后再点返回 `ALREADY_SUCCEEDED`。
- 重放使用 30 秒 token 租约与条件更新；并发重放只有一个领取者，租约丢失不能覆盖新主人的结果。处理已创建告警但回写失败的情况时，下次重放由告警外部 ID 继续幂等收敛。
- 新的合法实时 webhook 如果命中同一拒绝键，会自动将台账转为 `SUCCEEDED`，不要求值班人再做无意义操作。

## 可证伪验收

1. 对同一 fingerprint/start/status 投递两次，即使 firing `endsAt` 不同，也必须返回同一 rejection ID，`delivery_count=2`。
2. payload 中的明文 Token 和 Authorization 不得出现在数据库快照或列表 API，但必须保留已脱敏字段计数。
3. 重复坏投递不得清除已有重放租约；第二个领取者必须收到 `ALERTMANAGER_REPLAY_IN_PROGRESS`。
4. 修复 CMDB 后两个管理请求并发重放，最终只能有一条 alert 和一条成功审计；之后重放返回 `ALREADY_SUCCEEDED`。
5. AUDITOR 能查看但重放返回 403；OPS_MANAGER 在页面可见“重放”操作。
