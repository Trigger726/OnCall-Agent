## 1. 基本信息

## 2. 基线审计与候选口径

### 2.1 已确认的现状

1. `alert_event.fingerprint` 已由来源、资源、严重等级和规范化标题计算 SHA-256；30 分钟内相同指纹只增加 `occurrence_count`，超出窗口才产生新的告警事实。
2. `alert_event.incident_id` 和 `incident.service_resource_id` 能区分“同一 Incident 内重复告警”与“同一故障模式跨 Incident 再次发生”。
3. 现有 Postmortem 已保存根因与行动项，但每份复盘只属于一个 Incident；没有跨事故 Problem、已知错误、规避方案或持久化关联。
4. 当前数据没有经过人工确认的语义相似标签，直接宣传向量聚类准确率没有证据，因此本轮采用高精度、低召回的确定性基线。

### 2.2 决策规则

- 查询窗口按 Incident `created_at` 纳入，`from/to` 均包含，默认最近 90 日，最长 366 日。
- 候选簇要求同一 `alert_event.fingerprint` 关联至少 2 个不同 Incident；计数使用 `COUNT(DISTINCT incident_id)`。
- 同一 Incident 内 `occurrence_count = 100` 仍只算 1 个 Incident，不把告警噪声误报为 100 次复发。
- API 必须返回匹配依据 `EXACT_ALERT_FINGERPRINT`、首次/最近 Incident、不同日期数、未关闭事故数和告警发生总量；不返回伪造的概率或相似度分数。
- 管理角色把候选提升为 Problem 时固化当前匹配 Incident；以后新接入的同指纹 Incident 自动幂等关联。
- Problem 状态为 `OPEN / KNOWN_ERROR / RESOLVED`。进入 `KNOWN_ERROR` 必须同时提供根因和规避方案；进入 `RESOLVED` 必须提供解决说明；已解决后再次出现匹配 Incident 只标记复发事实，不静默冒充仍然有效的解决方案。

## 3. 成熟产品参考与本项目取舍

- [PagerDuty Related Incidents](https://support.pagerduty.com/main/docs/related-incidents) 区分历史相似 Incident 与当前跨服务相关 Incident，并展示匹配原因、时间线和人工反馈。OpsPilot 本轮只实现有直接数据证据的“历史精确指纹复发”，不复制其机器学习能力。
- [FireHydrant Alert Deduplication](https://docs.firehydrant.com/docs/alert-deduplication) 明确区分窗口内去重与窗口结束后的新告警事实；OpsPilot 用不同 Incident 数量作为复发分母，避免把一次事故内的重复信号当成多次事故。
- [Atlassian ITIL Problem Management](https://support.atlassian.com/jira-service-management-cloud/docs/what-is-the-itil-problem-management-process/) 将趋势发现、关联 Incident、按频率/影响排序、根因、规避方案、已知错误和关闭作为连续流程。OpsPilot 选取其中能够由现有证据验证的最小闭环。
- [Atlassian Known Errors](https://support.atlassian.com/jira-service-management-cloud/docs/how-to-document-known-errors-in-a-confluence-knowledge-base/) 要求已知错误包含问题、根因、症状和规避方案。OpsPilot 将根因与规避方案设为 `KNOWN_ERROR` 的服务端门禁，不只依赖页面提示。

## 4. 实现与验证记录

### 4.1 后端第一轮：模型、API 与 H2 定向验收

- Flyway V15 新增 `problem_record` 与 `problem_incident_link`：同一“归属服务 + 告警指纹”只能有一个 Problem，同一 Incident 也只能关联一次；状态、负责人、创建/解决人、根因、规避方案、解决说明和版本均持久化。
- `GET /api/v1/problems/recurrence-candidates` 已实现 90 日默认窗口、366 日上限、服务筛选、分页、精确匹配原因、独立 Incident/日期计数、未关闭数、总告警次数和最多 8 个 Incident 下钻。

- Alert Intake 在告警关联 Incident 后会查找已登记的精确指纹 Problem，新增唯一关联和 `PROBLEM_LINKED` 时间线；重复接入同一外部事件不会重复写关联。
- `ProblemManagementIntegrationTest` 在 H2 空库执行 V1–V15 后通过。用例同时构造同一 Incident 内 110 次告警噪声和跨两个 Incident 的 102 次精确指纹信号，证明前者不成簇、后者只形成一个候选；随后覆盖普通值班员 403、重复提升幂等、已知错误字段门禁、陈旧版本 409、解决、解决后新增 Incident 自动关联、复发标识、非法流转、重新打开及审计数量。

## 6. 边界与后续

- 当前确定性规则偏向精确率，标题规范化或严重等级变化会形成不同指纹；这属于已知的召回边界，不应用降低门槛或伪造分数掩盖。
- 语义相似、依赖共因和时间邻近聚类需要脱敏历史标签、阈值校准、人工反馈与离线 Precision/Recall 对照后再进入主流程。
- 已解决后复发目前要求负责人手动重开；后续可增加复发 SLA、通知与决策待办，但不能由后台规则直接覆盖人工结论。
- `problem_record` 当前由一个较集中的领域服务承载查询与命令。若后续加入外部工单同步、SLO 优先级或语义聚类，应按读模型/命令处理拆分，而不是提前为本轮小闭环引入额外抽象。
- Flyway 版本仍提示 MySQL 8.4 超出其官方验证上限；依赖升级后继续保留真实 MySQL 与容器门禁。
