# OpsPilot V1.7 验收报告：检查点 02

## 1. 基本信息

- 验收日期：2026-09-02
- 验收主题：事故响应指标与防复发行动项运营
- 当前状态：本地验收通过，待远端 CI
- 计划范围：MTTA/MTTM/MTTR 口径与样本分母、慢事故明细、全局行动项视图、逾期事实与幂等升级、H2/MySQL/响应式页面验证
- 暂不纳入：外部消息渠道、跨 Incident 相似聚类、分布式事件与 OpenTelemetry

本检查点承接 V1.7 checkpoint 01：复盘已经能形成有负责人和期限的防复发行动项，但负责人离开单次 Incident 后没有统一待办，管理者也无法判断响应耗时与逾期积压。目标是把“写了复盘”继续推进为“能持续运营和追责事实、但不制造虚假通知能力”的闭环。

## 2. 基线审计与验收口径

### 2.1 已确认的现状

1. 首页 `mttaMinutes` 对所有已确认 Incident 求单一平均值，没有查询时间窗、严重等级过滤、样本数或中位数；缺失里程碑的排除规则对使用者不可见。
2. `incident` 已保存 `created_at / acknowledged_at / resolved_at`，`MITIGATED` 只存在于不可变时间线，可以在不新增重复事实字段的前提下重建三个响应里程碑。
3. 行动项目前只能随单份复盘返回；已有负责人、截止日期、状态和乐观锁，但没有跨复盘列表、逾期状态、升级记录或定时扫描。
4. 现有 `notification_log` 表示 Incident 通知发送事实。当前没有真实邮件、短信或企业 IM 连接器，因此本检查点不会把数据库插入冒充成“消息已送达”。

### 2.2 指标定义

- 查询窗口按 Incident 的 `created_at` 日期纳入，`from/to` 均包含；默认最近 30 个自然日，最长 366 日。
- MTTA = 首次确认时间 - Incident 创建时间。
- MTTM = 时间线中首次进入 `MITIGATED` 的时间 - Incident 创建时间。
- MTTR = 首次恢复时间 - Incident 创建时间。
- 每个指标只统计自身里程碑存在且不早于创建时间的样本，并同时返回样本数；不能把缺失值按 0 分钟计算。
- 均值用于总体容量判断，中位数用于降低少量极慢事故的影响；慢事故明细用于回到具体 Incident 核查。
- 行动项在 `status = OPEN` 且 `due_date < asOf` 时逾期；截止当天不算逾期。
- 事故指标受 `from/to/severity` 过滤；行动项摘要始终标注当前 `Asia/Shanghai` 业务日期，不伪装成具备历史状态回溯能力的时态快照。

## 3. 成熟产品参考与本项目取舍

- [FireHydrant Incident Milestones](https://docs.firehydrant.com/docs/incident-milestones-lifecycle-phases) 给出 detection、acknowledgement、mitigation、resolution 相对 Incident 开始时间的定义；OpsPilot 采用其中 MTTA/MTTM/MTTR 三项，并明确暴露每项分母。
- [PagerDuty Incident Activity Insights](https://support.pagerduty.com/main/docs/incident-activity-insights) 对 MTTA/MTTR 排除未确认和未恢复事故，并提供平均值、中位数等分布视角；OpsPilot 本轮使用平均值、中位数和慢事故下钻，不在小样本上包装复杂百分位。
- [Rootly Action Items](https://docs.rootly.com/incidents/action-items/action-items) 将行动项集中展示并按负责人、期限、状态持续跟踪；[Rootly SLA Policies](https://docs.rootly.com/incidents/action-items/sla-policies) 将逾期违规保留到行动项完成。OpsPilot 将此原则实现为应用内、持久化、幂等的逾期事实，不宣称已经完成外部渠道送达。

## 4. 实现与验证记录

### 4.1 后端第一轮：模型、API 与 H2 定向验收

- Flyway V14 从时间线回填历史 Incident 缺失的 `resolved_at`，新增一行动项一记录的 `postmortem_follow_up_escalation`；记录截止日期快照、首次发现业务日期、创建人和关闭事实，不覆盖原行动项。
- `GET /api/v1/analytics/incidents` 已实现 30 日默认窗口、日期/严重等级过滤、366 日上限、三个指标的均值/中位数/独立样本数、严重等级分布和最慢恢复明细。
- `GET /api/v1/postmortem-follow-ups` 已实现全部/本人、状态、逾期和业务日期过滤；返回 Incident、负责人、逾期天数和升级状态。
- 管理员/运维经理可显式运行逾期扫描，每日 09:05 按 `Asia/Shanghai` 自动扫描；同一行动项行锁串行化后检查唯一事实，重复扫描不重复写时间线与审计。
- 行动项完成事务会同步关闭开放升级事实，并追加独立的时间线与审计事件；没有逾期事实的正常完成不产生额外记录。
- `IncidentAnalyticsIntegrationTest`：H2 空库执行 V1–V14；构造已完成、缺失里程碑和负时长三类样本，精确验证 MTTA 6.5、MTTM 27.5、MTTR 50.5 分钟及各自分母，负时长不出现在慢事故明细；同时验证错误窗口和非法严重等级。
- `FollowUpOperationsIntegrationTest`：第二个 H2 空库执行 V1–V14；验证逾期/截止当天/已完成三类行动项、本人过滤、角色 403、首次/重复扫描、唯一升级事实、一次时间线与审计、完成后关闭及逾期列表归零。
- 两个定向测试共 2/2 通过，失败/错误/跳过均为 0。

### 4.2 全量回归与真实数据库

- 默认 H2 套件发现 21 个测试套件、37 项测试；36 项执行通过，失败/错误为 0，1 项需要显式启用 Docker 的 MySQL 条件测试按设计跳过。

### 4.3 前端、JAR 与真实页面

- 新增“运营分析”入口：日期/严重等级筛选、四张指标卡、均值/中位数/样本数、慢事故下钻、严重等级分布、全局行动项筛选、管理角色逾期扫描和负责人完成入口。
- 页面显式提示“升级”只代表应用内持久化事实、时间线和审计，不代表邮件、短信或企业 IM 已送达。
- 前端生产构建通过：1608 个模块，CSS 90.33 kB（gzip 17.00 kB），JS 226.20 kB（gzip 75.37 kB）；构建产物已进入最新 JAR。
- 使用最新 JAR 和隔离 H2 文件库登录真实页面。桌面端实际显示 2 个 Incident、MTTA 3 分钟（n=2）、MTTM 25 分钟（n=1）、MTTR 41 分钟（n=1）以及 1 个逾期行动项；点击“运行逾期扫描”后状态从“未升级”变为“已升级”。
- 真实深链 `/analytics` 首次暴露 JAR 内 SPA 路由没有回退到 `index.html`，已增加显式前端路由转发并补集成测试。390×844 视口首次暴露宽表将页面撑到 584 px，已改为页面不横向溢出、表格内部滚动；复测文档宽度 380 px、视口 390 px。

### 4.4 历史数据兼容与事实边界

- V14 只用首次 `RESOLVED` 时间线回填历史缺失的 `incident.resolved_at`，不改写已有恢复时间；负时长继续由指标查询排除。
- 升级记录是独立事实表，不复用 `notification_log`，避免把“发现逾期”与“外部通知送达”混为一谈。
- 同一行动项最多一条升级记录；完成后记录从 `OPEN` 变为 `RESOLVED`，保留首次发现、创建人和关闭人/时间，后续查询仍可解释其历史。

## 6. 尚未实现的边界

- 没有邮件、短信、企业微信等真实外部渠道、确认回执和重试死信；当前“升级”是内部可审计事实。
- 没有跨 Incident 相似聚类、重复事故率、Runbook 命中率趋势、按服务/SLO 的目标线与长周期时间序列。
- 没有 Kafka/Redis Streams 多实例事件分发、OpenTelemetry Trace，以及模型 Provider 原生 token 流。
- 行动项摘要是当前状态，不支持按历史日期重建当时的负责人、状态或完成率。
