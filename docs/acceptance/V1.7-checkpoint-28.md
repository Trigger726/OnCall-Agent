# V1.7 checkpoint-28：多窗口错误预算燃烧率

日期：2026-09-22。状态：本地通过。后端计算、全量自动化、前端测试与生产构建、JAR 以及启用/关闭两种真实页面状态均已通过；远端七项门禁待复核。

## 为什么 checkpoint-27 的累计 SLI 还不够

[Google SRE Workbook](https://sre.google/workbook/alerting-on-slos/) 建议用多窗口、多燃烧率同时兼顾检出时间、精度和恢复时间；长窗口和短窗口必须同时超阈值，避免已经恢复的历史峰值继续告警。成熟开源项目 [Sloth](https://github.com/slok/sloth) 也把多窗口燃烧率和自动生成 Prometheus 规则作为核心能力。因此本检查点在累计错误预算之上增加“当前是否正在快速燃烧”的运营信号。

## 实现与口径

- 燃烧率为 `((total - good) / total) / (1 - target)`；`1x` 表示按当前速度刚好在 SLO 周期末耗尽预算。
- 固化三档 Google SRE 起始参数：急速 PAGE `1h + 5m / 14.4x`，持续 PAGE `6h + 30m / 6x`，工单 `3d + 6h / 1x`。每档都是长/短两窗口的 AND，整体按急速 PAGE、持续 PAGE、工单的顺序取最高行动级别。
- `6h` 在两档中共享一份查询样本，总共评估 `5m / 30m / 1h / 6h / 3d` 五个唯一窗口。
- 每档返回长/短窗口燃烧率、分母、阈值和状态。空结果、零分母、矛盾计数和 Provider 失败仍显式拒算；Prometheus 关闭时不发起查询。
- 运营分析页在原有累计 SLI/错误预算旁展示三档燃烧率，保留 checkpoint-27 的目标编辑与异常状态。

## 可证伪验收

1. 99.9% 目标下，1h 为 20x 但 5m 为 0.5x 时不得 PAGE，证明不是 OR 或单窗口判定。
2. 1h/5m 同为 15x 时必须是 `PAGE_FAST`；6h/30m 同为 7x 时是 `PAGE_SLOW`；3d/6h 同为 2x 时是 `TICKET`。
3. 零分母或 `good > total` 的窗口不得生成燃烧率。
4. Prometheus 关闭时返回 `PROVIDER_DISABLED`、窗口列表为空，页面不显示任何种子燃烧率。
