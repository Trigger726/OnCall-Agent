## 2. 本轮新场景

新增继承同一场景的 H2 TCP 与自有 MySQL Testcontainer 两个测试入口。测试启动真实生产JAR，不使用Spring Mock/Spy或新增生产测试API；两个应用进程同时存活并共享同一自有SQL数据库。A退出后再启动一个独立进程，故总共3个应用JVM生命周期，而不是3节点集群或跨机器/HA验证。

6个真实HTTP流程：

1. A/B同时释放捕获原成员命令，回执相同，SQL只一台账/一审计。
2. B撤权后A新认领/管理403；原成员回执只读保留，当前行版本可更高；跨计划/异内容键409、旧版本409，无自动重基或SQL写入。
3. A认领已提交且收到200状态行时关闭真实socket、不读取响应体；B手动求原回执、独立取消覆盖；A重启后原回执不变，新键409，不复活覆盖。
4. 经理撤销自己的计划管理后，B原键200、新管理403；同一旧JWT的当前角色改为auditor后A/B均403，恢复全局角色不恢复计划管理。角色变化仅使用该自有库的明确测试夹具SQL，不动用户业务库。
5. 两个有效计划，原成员A计划可响应、B计划403；B计划的合格成员对照200，不把无效计划/源当授权拒绝。
6. 两活跃节点同时认领同原键，只一次覆盖/原操作，准确2条责任审计。

最终独立JDBC核对5请求/4CLAIMED/1OPEN、4认领台账、5成员台账/5成员审计，实际V39/39版本化迁移。每次拒绝/手动确认比较六张业务表完整行摘要。并发由双请求准备屏障释放，不靠长sleep；本轮不宣称每个跨节点场景观察了SQL锁等待，已有真实锁等待顺序证据仍来自共享22场景。
