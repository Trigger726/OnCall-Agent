## 真实运维能力

原调度器在一worker忙时拒绝本次tick，不保存在内存队列中，事件仍在SQL；此前拒绝次数和全局积压无法观察。本轮新增[运行状态接口与操作说明](../ONCALL_OPEN_NOTIFICATION_OPERATIONS.md)：`GET /api/v1/on-call/open-notification-operations`。

数据库统计为一条SQL同一事实时间：PENDING总数/已到尝试时间、CLAIMED/已过租约、DELIVERED、FAILED、SKIPPED和最早排队创建时间。另列本进程活跃worker、零等待tick、忙拒绝、批次异常、关闭状态；明确数据库与本地executor不是原子快照，计数重启清零且不是HA全局指标。忙拒绝不是丢失事件，也不等于渠道或人接班。

全局观察仅当前有效ADMIN可读，HTTP方法权限和数据库身份双重检查；审计员、ON_CALL、运维经理及撤权旧管理员拒绝。无收件人/请求ID/投递键/正文/渠道/令牌，无新写命令。SQL失败503且无零积压/旧缓存回退。保持原同事务outbox、稳定键/正文、资格重查、租约CAS、一线程零内存队列及原22网络契约不变；不新增DDL或自动重投/认领。

## 真实失败与修复

首次新JAR真实TCP负例中，不支持的POST落到通用异常处理器，记录 `Unhandled request error` / `HttpRequestMethodNotSupportedException`，500而不是405。原失败完整两JVM日志保留。最初临时runner在finally日志断言处又抛错，没有result.json；不得把它称为完整PASS。随后保留实际未修复包（SHA `17cdca31666c24b11dc01249edf2068fd5688609212e22335572e5f6e2d7b360`）重新真实请求，明确记录500/INTERNAL_ERROR，作为独立历史负对照。

生产修复只增加对应异常的显式405 JSON、`METHOD_NOT_ALLOWED`与Allow头，不回显方法/路径/正文，不将正常方法错误记作意外ERROR。新增方法负例验证通知事件字节不变。最终runner明确区分“已记录HTTP500且异常类别匹配的历史未修复JAR唯一日志错误”和新JAR日志；后者严格零意外ERROR，不泛化忽略任何新错误。
