日期：2026-09-27。状态：本地通过；旧快照误路由已复现并修复，双时区全量、八项 H2 提交闸门/回滚场景与前端测试通过，真实 MySQL/远端门禁待续验。

## 问题与决策

checkpoint 43 的单次取消后再创建新告警已经通过，但未覆盖“接入/扫描事务先读快照 → 另一事务提交取消 → 原事务继续选择负责人”的交错。以连接池默认 REPEATABLE_READ 的独立 H2 启动实际 `AlertService.intake`，受控暂停在即时路由前；取消覆盖事务完成后再放行，旧代码仍将通知记给 `lina` 而不是普通班次用户。失败命令与结果保存在 [regression-before.json](assets/V1.7-checkpoint-44/regression-before.json)，不以 H2 结果冒充 MySQL 实测。

[MySQL 8.4 事务隔离说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) 指出 REPEATABLE_READ 的普通读复用初次快照，READ_COMMITTED 每次普通读建立新快照；[锁定读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) 提供最新读取，但直接对旧 H2 快照增加 FOR UPDATE 实测出现 40001 序列化冲突，因此未采用该跨数据库不一致的方案。

告警接入、升级扫描以及独立即时路由的事务入口显式使用 READ_COMMITTED。即时路由仍加入告警接入的同一事务，Incident 行锁与 `(incident_id, step_id)` 唯一约束继续保证步骤防重；没有拆出新连接读、异步补记或修改全局隔离级别。更高层调用若已有事务，Spring 的 REQUIRED 会加入该事务，不自动覆盖其隔离级别；当前 HTTP/定时扫描入口均由这些服务建立事务，未来外层事务需保持这一契约。

保证边界是：提交发生在对应的策略/班次/用户查询前，则该查询可见；选择后才发生的变动不追溯撤回已有路由。不是将取消与路由串行化，也不承诺外部送达 exactly-once。用户停用、计划/策略停用和角色变更由隔离测试夹具模拟，不意味着本轮新增了管理入口。
