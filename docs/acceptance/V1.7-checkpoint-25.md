# V1.7 checkpoint-25：跨 JVM CLIENT/SERVER Trace 拼接

日期：2026-09-19。状态：部分通过。独立 fixture JAR 打包、本机启动和 Prometheus/Loki 兼容响应已通过；Docker/Tempo 真实跨服务门禁待远端 GitHub Actions 验证。V1.7 整体仍在持续迭代。

## 前一检查点留下的问题

checkpoint-24 已用真实 TCP 端点证明 OpsPilot 发出的 `traceparent` 与 HTTP CLIENT span 一一对应，但端点本身没有 tracing SDK，也没有把 SERVER span 导入 Tempo。它只证明发出端正确，不能证明分布式 Trace 在服务边界另一侧接续。

## 实现与范围

- 新增独立 Maven/Spring Boot 应用 `integration/trace-provider-fixture`。两个只读 HTTP 端点分别返回合法 Prometheus vector 与 Loki streams 响应；Spring Boot/Micrometer/OpenTelemetry 对请求自动产生 SERVER span，并经同一 Collector 导出。fixture 只在 Compose `tracing-test` profile 启动，不进入 OpsPilot 生产 JAR，也不在普通 `tracing` 演示中启动。
- CI Trace 脚本在隔离的 Compose project 中开启 OpsPilot Prometheus/Loki Provider，令其真实访问 fixture；默认 `docker compose up` 的 Provider 开关仍关闭。
- 从 Tempo 原始 `batches[].resource.attributes` 提取两个服务的 `service.name`，检查恰有 2 个 `opspilot.provider.query`、2 个 OpsPilot `SPAN_KIND_CLIENT` 和 2 个 fixture `SPAN_KIND_SERVER`；SERVER 的两个 parentSpanId 必须与 CLIENT 的两个 spanId 一一相等，所有相关 span 必须共享唯一 traceId。
- 同一断言分别用于正常调查与 Tempo 短暂停机后恢复的调查；原有 `1 run / 6 tool / 2 provider`、Grafana 读回、业务 `COMPLETED`/健康 `UP`、Collector 真实失败日志、敏感哨兵排除均保留。

## 当前直接证据

- `./mvnw -f integration/trace-provider-fixture/pom.xml -DskipTests package`：`BUILD SUCCESS`，生成独立可执行 JAR。
- 本机独立 JVM 启动后，`/actuator/health` 为 `UP`；两个 Provider 端点分别返回 `success/vector/1` 与 `success/streams/1`。
- `docker compose --profile tracing --profile tracing-test config --quiet` 与 `bash -n scripts/verify-tracing-pipeline.sh`：静态检查通过。
- 本机 Docker Desktop daemon 当前不可用，所以不能把配置和 JAR 启动结果代替真实容器/Tempo 父子链路证据。远端 CI 是本轮交付门禁。

## 可证伪验收

1. Compose 启动 OpsPilot、独立 fixture、Collector、Tempo、Grafana；fixture 和 OpsPilot 健康均为 `UP`。
2. 一次真实告警的六工具调查返回 `COMPLETED`，TraceQL 按 run ID 找到 trace，Grafana 读回同一 trace。
3. Tempo 内同时存在两个不同 `service.name`；两个 HTTP CLIENT span 必须由 `opspilot.provider.query` 直接派生，两个 fixture SERVER span 必须以这两个 CLIENT spanId 为 parent，traceId 只能有一个。
4. 停止 Tempo 后再次完成调查，OpsPilot 仍健康，Collector 确实记录导出失败；Tempo 恢复后必须重新满足上述跨服务父子断言。
5. 两次 trace 都不得包含动态敏感哨兵。任一条不满足则本检查点不通过，不用“都能查到 span”替代严格父子关系。

## 边界

- fixture 返回兼容协议，但不是生产 Prometheus/Loki 集群，不宣称验证其真实 tracing instrumentation、TLS、网关或多租户配置。
- Collector 当前仅内存发送队列；本轮只覆盖其进程存活时的 Tempo 短暂停机，不保证 Collector 重启后零丢失。
- 生产采样率、跨信任边界 context 策略、对象存储与高并发成本仍待验证。

## 依据

- [OpenTelemetry Context propagation](https://opentelemetry.io/docs/concepts/context-propagation/)：通过 W3C `traceparent` 跨进程传输 traceId 和父 spanId。
- [OpenTelemetry Trace API](https://opentelemetry.io/docs/specs/otel/trace/api/)：传递 CLIENT span context 后，远端 SERVER span 通常是其子节点。
- [Spring Boot 3.2 tracing](https://docs.spring.io/spring-boot/docs/3.2.x/reference/html/actuator.html#actuator.micrometer-tracing)：自动 HTTP 观测和 OTLP 配置依据。
