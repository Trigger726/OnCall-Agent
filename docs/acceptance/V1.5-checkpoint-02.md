## 3. 真实 MySQL 验证范围

MySQL 用例不是只做一次连接探测，而是验证：

1. 由 Testcontainers 启动 `mysql:8.4`，Spring Boot 通过 service connection 使用容器提供的数据源。
2. Flyway 从空 schema 依次执行 V1-V6，最终版本为 6 且所有迁移成功。
3. 读取中文种子数据，避免只验证 ASCII 和表结构。
4. 从数据库元数据确认 `uq_agent_run_idempotency` 是由 Incident ID 和幂等键组成的双列唯一索引。
5. 使用相同幂等键连续准备两次调查，第二次复用原 run，数据库中只存在一条记录。
6. 真正执行调查并得到 `COMPLETED`、1 份报告、9 个步骤和 18 个有序事件；首事件为 `RUN_QUEUED`，末事件为 `RUN_COMPLETED`。

Testcontainers 用例默认跳过，避免没有 Docker 的普通开发机无法执行快速回归；CI 使用 `opspilot.mysql.it.enabled=true` 显式开启，因此 Docker 或 MySQL 启动失败会让独立门禁失败，而不会静默跳过。

## 5. 本检查点发现并修复的问题

1. 仅依赖 `flyway-core` 时，H2 全量测试正常，但真实 MySQL 启动报 `Unsupported Database: MySQL 8.4`。补充 `flyway-mysql` 后再跑同一用例通过，没有弱化数据库断言。
2. 首次镜像可以成功构建，但运行时的非 root 用户无法创建 `/app/data`，默认 H2 启动失败。Dockerfile 现在预建目录并只授予应用用户所需写权限，重建和健康启动均通过。
3. README 与检查点 01 曾把三个线程池环境变量写成 `AGENT_EXECUTOR_*`，实际配置是 `AGENT_CORE_POOL_SIZE / AGENT_MAX_POOL_SIZE / AGENT_QUEUE_CAPACITY`；本次已统一。

## 6. GitHub Actions 门禁

工作流对 `main`、`master`、`feat/**`、Pull Request 和手工触发生效，并使用最小 `contents: read` 权限及同分支旧运行自动取消：

1. `frontend`：Node 22，`npm ci && npm run build`。
2. `backend-h2`：Temurin 17，完整 `mvn package`，同时产出测试证据和 JAR。
3. `mysql-integration`：显式开启 Testcontainers MySQL 用例。
4. `container-image`：只在前三个 job 全部通过后执行；构建镜像、启动临时容器并轮询健康端点，最后无论成功失败都清理临时容器。

Linux runner 会先给仓库中的 Maven Wrapper 增加执行权限，避免当前 Windows 工作区中的文件模式导致 CI 直接失败。

本机 Codex 进程的 `PATH` 含一个非 Windows 格式片段，运行 Testcontainers 前仅在当前 PowerShell 进程中排除了该片段；这是本机测试工具环境问题，未写入项目配置或 CI。

## 8. 当前边界

- 本地已经执行与四个 CI job 对应的前端、H2、MySQL、镜像和健康启动验证，但没有代码推送权限范围内的托管 Actions 运行记录。
- SSE 断开单测覆盖发送适配器的 `IOException` 隔离；V1.4 已做真实浏览器重连与游标回放，后续仍可增加代理层强制 TCP 断流和长时间并发 soak test。
- 有界队列测试验证确定性饱和语义，不等同于吞吐量或容量结论；系统级压测仍需基于目标部署规格定义 SLO 后执行。
- 当前任务协调是单实例内存执行器；多实例幂等、取消和事件广播仍需外部协调组件。
- Flyway 9.22.3 对 MySQL 8.4 给出“高于已测试版本”提示，虽已通过本项目实际迁移与业务链路，后续依赖升级仍应重新执行同一门禁。
