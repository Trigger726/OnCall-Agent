# OpsPilot V1.7 检查点61：Collector 崩溃与队列恢复

## 阶段一：先补故障实验（2026-10-02）

结论：实现待验，不宣称持久化恢复通过。生产配置仍为原内存队列，先用真实 Linux Compose 证明丢失范围，再补持久化。

- 基线 `c3ec124` 的 [Run36997016999](https://github.com/Trigger726/OnCall-Agent/actions/runs/36997016999) 已完成十三作业 success；现有正常 Trace 和 Tempo 单独停机恢复继续保留。
- 新第三阶段：Tempo 停机 → 注入已知 W3C Trace ID 的真实调查（业务 COMPLETED、健康 UP）→ 等待两个 JVM 导出及 Collector 积压 → SIGKILL → 强制重建不同 ID 的 Collector 容器（Tempo 仍停止）→ 恢复 Tempo → 核对原 Trace ID、原 runId、六工具和两条 Provider→CLIENT→SERVER 父子链，不重新提交调查。
- 指标采集和单消费者只存在于测试覆盖配置；生产默认十消费者不改。队列单位是导出请求/批次，不是 Span。接收计数增量只证明总量，不能冒充目标 Trace 的持久确认。
- 单独的合成 blocker Trace 先占用测试消费者，避免两 JVM 导出被合为单个在途请求而没有可观察积压；成功证据仍只认真实调查的完整原 Trace，绝不以 blocker 的恢复代替。
- 原断言处于 Bash `&&` 条件调用，`set -e` 不足以阻止函数内早期失败；本次为每条结构断言增加显式 `|| return 1`，避免只靠最后一条命令返回值误报通过。
- 本机 Docker Desktop Linux daemon 当前不可用；WSL Bash 静态校验与 YAML 解析不替代真实远端故障实验。
