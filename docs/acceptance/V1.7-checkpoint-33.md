# V1.7 checkpoint-33：Prometheus 规则到 Incident 的真实链路

日期：2026-09-23。状态：通过。隔离规则夹具、联调脚本和第九项 CI 门禁已加入；[Run 35854884221](https://github.com/Trigger726/OnCall-Agent/actions/runs/35854884221) 九项门禁全部通过。

## 目标与边界

checkpoint-32 使用真实 Alertmanager，但告警由脚本直接 POST 到其 Alerts API v2。此轮增加真实 Prometheus 规则求值：短时测试指标从 Pushgateway 被 Prometheus 抓取，`for: 2s` 后规则进入 firing，并通过 Alertmanager 的现有鉴权 receiver 进入 OpsPilot；把指标改回正常值后验证恢复落在同一 Alert。Prometheus 的[规则文档](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)定义 pending、firing 与恢复语义，[配置文档](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)定义 Alertmanager 目标。Pushgateway 只用于此处隔离、可控的测试指标；[官方实践](https://prometheus.io/docs/practices/pushing/)不推荐把它作为通用在线服务指标的生产采集路径。

## 可证伪验收

1. Prometheus `/api/v1/rules` 必须加载目标规则；`/api/v1/alerts` 必须先显示 `firing`，指标复原后不再显示活跃状态。
2. OpsPilot 必须从 Alertmanager 收到同一规则的 firing，形成一条 `FIRING:1` Alert；规则恢复后同一 ID 变为 `RESOLVED:1`，并有且仅有一条 `ALERT_RESOLVED` 时间线。
3. 此规则不得产生拒绝台账项；脚本不直接调用 Alertmanager Alerts API v2 或 OpsPilot 的成功接入 API。
4. 使用隔离 Compose project/volume 与运行时测试密钥，退出清理；保存 Prometheus 规则/状态、数据库摘要和容器日志用于失败诊断。
