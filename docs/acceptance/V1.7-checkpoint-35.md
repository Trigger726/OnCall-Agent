# V1.7 checkpoint-35：逾期行动项外部提醒与投递回执

日期：2026-09-23。状态：部分通过。可靠投递与数据库门禁已闭环；真实第三方渠道、人工确认及页面浏览器验收尚无证据。

## 动机与边界

checkpoint-02 的逾期扫描会在 OpsPilot 内生成唯一升级事实、时间线和审计，但不向外部系统投递。成熟 Incident 工作流强调行动项的明确负责人、期限和持续提醒；[incident.io 的事后行动项实践](https://incident.io/blog/why-do-post-mortem-action-items-fail-how-to-make-incident-follow-ups-actually-get-done)也将跟进节奏和投递到团队实际工作渠道视为闭环条件。本轮增加默认关闭的通用 HTTP webhook，不绑定某一家消息平台。

投递状态与人的确认必须分开：`DELIVERED` 仅表示配置的接收端返回 HTTP 2xx，不代表负责人已读或已执行。生产接收端需按 `Idempotency-Key` 去重；网络超时后无法区分“未送达”和“已接收但回执丢失”，系统按至少一次投递处理。

## 可证伪验收

1. 仅在通知显式开启时，首次逾期升级与通知行同事务创建；重复扫描不重复入队，事务回滚不留孤儿通知。历史关闭配置的 Demo 行为不变。
2. 调度器以条件租约领取，HTTP POST 发送入队时冻结的行动项摘要、Bearer 鉴权和稳定幂等键；后续编辑不改变同键载荷，并发领取仅有一方成功，领取后检查时已关闭的升级标记 `SKIPPED`。
3. 2xx 记录端点接受时间；503/429/传输错误按有上限的指数退避重试；其他 3xx/4xx 或耗尽次数进入 `FAILED`。不保存远端响应正文或密钥。
4. 管理员/运维经理可对仍开放的失败通知受控重试，其他角色被拒；列表和运营页面清楚显示通知状态、尝试次数及 HTTP 状态，不将技术回执描述为人工确认。
5. Flyway V22 在 H2 与 MySQL 8.4 空库迁移通过；后端、前端构建和远端 CI 不回退。
