## 业务边界与实现

原能力只能在班次维护中取消覆盖，接班台账仍显示“已接受，去核对日历”。新增 `GET /api/v1/on-call/handoffs/{id}/coverage`，单条联表语句同时读取数据库快照时钟、原请求、实际覆盖行及独立撤销事实。实际覆盖取消不伪造为请求WITHDRAWN；接受人、接受时间、请求版本/理由与原班次保留。班次维护已有直接取消也能读到实际取消，但不会虚构新撤销记录。

`POST /api/v1/on-call/handoffs/{id}/coverage/revoke` 只允许当前活跃ADMIN/OPS_MANAGER，既检查控制器角色又锁定数据库最新角色，旧JWT不能维持已撤销职责。沿用现有管理取消权限，不把撤销设计成普通ON_CALL单方解除已接受责任。请求体包含捕获的请求/覆盖版本、规范UUID operationKey和1–500字说明。

计划→请求→管理人行锁；同管理人的键跨计划串行化。V28独立表以请求ID主键、管理人+键唯一，保存原版本和不可变意图。未结束覆盖可取消，过期新操作拒绝；已提交的同键/同版本/同说明重试可回原事实，即使之后时段结束，但仍要求当前管理资格。不同内容/请求复用同键409，新键面对已取消覆盖也409，不自动换版本、换键或复活覆盖。

覆盖软取消、撤销台账、班次审计和请求关联审计同事务，任一审计失败全回滚。请求ACCEPTED状态不改，原接受决定的幂等回执仍有效；既有站内通知、Incident路由事实与历史Demo不重写。不承诺取消后一定回到原负责人：原班次也可能已取消或账号/计划无资格，须核对覆盖日历。现有日历是当前规则下的覆盖预览，不是历史责任时点重建。

参考 [PagerDuty删除覆盖API](https://docs.pagerduty.com/developer/api/reference/rest/schedules/delete-schedule-override) 对已过去覆盖的限制、[保留排班历史原则](https://support.pagerduty.com/main/docs/schedule-basics)；这是OpsPilot现有权限/软取消体系内的独立实现，不接入PagerDuty、外部通知或双向互换。
