> OpsPilot 是我把原 OnCall AI Agent 重构成的企业级故障闭环平台。它先对 Prometheus/APM 告警去重聚合，再结合 CMDB 形成 Incident，通过状态机、值班升级和审计完成闭环。调查部分采用可解释 Agent 工作流，按计划调用告警、拓扑、指标、变更、日志和 Runbook 六个只读工具；真实检索快照写前脱敏，并通过盲化双评分和 NDCG 形成可复现评测。步骤和实时事件先落库，再通过 SSE 推送并支持游标回放。事故恢复后从真实证据生成无责复盘，必须补全影响、原因和经验并绑定负责人/期限行动项，提交人不能自审，发布后正文冻结；运营页再按独立样本口径展示 MTTA/MTTM/MTTR，并对跨事故逾期行动项形成幂等、可关闭的升级事实。高置信度变更关联也只生成回滚草案，系统不会直接修改生产环境。

## 高频追问

### JWT签名有效，为什么停用账户仍需要入口资格校验？

签名只证明token由系统签发且未过期，不证明当前账户还可用。真实HTTP测试发现过滤器虽然重新加载了UserDetails，却直接构造已认证对象，停用账户仍能读身份和写事故备注。我在建立认证前调用标准账户资格检查，停用/删除返回统一401，活跃账户权限不足仍403；H2与MySQL共享真实网络/已提交状态场景，写拒绝还检查时间线和审计零新增。不是永久撤销：重新启用后未过期旧token可用，既有SSE/后台任务不追溯取消，相关边界见[59阶段证据](acceptance/V1.7-checkpoint-59.md)。

### 用户名查回当前账户，为什么还要比对Token里的uid？

用户名可被重新注册，但同名新账户不是原持有人。实际HTTP首失败显示旧uid=5的Token读到新id=6的ADMIN身份，还能写事故备注；仅重新查状态/角色不足以阻止身份转移。验证签发uid/sub/exp的类型与边界后，比对当前数据库ID，匹配才建立认证；拒绝读写为401、零业务新增，新账户用自己的新Token正常登录。测试覆盖大于JavaScript安全整数的精确ID，不能把小数或数字字符串转成另一个身份；角色仍来自数据库。该机制限正常分配新ID，人工复用原ID、数据库回滚与永久撤销另需会话策略，不能夸成完整身份生命周期。见[60证据](acceptance/V1.7-checkpoint-60.md)。

### 错误签名的Token为什么也可能触发500？

库先解析JSON时间字段再做签名检查，超出Instant范围的exp/iat/nbf曾直接抛DateTimeException。六项边界单测和真实HTTP的正确/错误测试密钥共12类输入确认500，不是“没有密钥就无法影响入口”。只将库验证范围内已复现的时间异常归为验证失败，复用结构化401；不能捕获所有异常或放行畸形Token。共享HTTP还断言业务零新增、正常请求仍200；实际JAR门禁用无关测试密钥即可重放。测试证明错误响应和异常日志，没有压力实验，不能宣称已量化DoS效果。

### SLO 页面已有燃烧率，为什么还要导出原生规则？

页面按需查询只能展示信号；Prometheus需要持续评估并交给Alertmanager处理投递与恢复。我让页面与导出共用预算策略，并要求导出捕获目标版本，变更后旧版本409，浏览器核验文件摘要。真实原生链路已在本机验证重复firing仍是一条告警、resolved只有一条恢复时间线。发布由运维执行，生产数据口径、长期历史和低流量政策仍需验证，详细证据见[检查点58](acceptance/V1.7-checkpoint-58.md)。

### 为什么不能把14.4、6、1写死在所有SLO周期？

这些值对应30天目标。阈值等于周期小时数乘预算比例再除以长窗口小时数，所以28天应为13.44、5.6、0.933333…；固定30天值会导致28天漏掉应快速处理的信号、90天过早PAGE。真实HTTP测试先复现了错误决策，再用同一策略修正页面与规则。1/2天目标还要缩短票据窗口，避免用超过目标周期的长窗口。

### 为什么 Alert 和 Incident 要分开？

Alert 是监控规则产生的观测事件，可能重复、抖动或来自同一故障的不同指标；Incident 是需要人负责、流转和复盘的业务事故。一对多建模后才能保留原始证据，同时避免值班人员处理几十条重复任务。

### 指纹为什么不用标题直接做唯一键？

同一个标题可能发生在不同服务和严重等级，且同一告警在恢复后再次触发应创建新事件。指纹包含来源、资源、等级和规范化标题，再配合活跃状态与 30 分钟窗口判断，不将所有历史告警永久合并。

### 并发流转怎么处理？

客户端读取 `version`，更新 SQL 使用 `WHERE id=? AND version=?` 并执行 `version=version+1`。受影响行数为 0 表示其他人先更新，返回 409 让客户端刷新。这样避免最后写入者静默覆盖前一个人的处置结果。

### 为什么不用微服务？

当前模块规模和团队规模不需要承担分布式事务、服务发现和链路排障成本。先用模块化单体明确领域边界；告警吞吐和通知可靠性真正成为瓶颈后，再拆 Alert Intake、Notification，并通过事件消息解耦。

### AI 怎样避免幻觉？

模型不拥有数据查询自由，只接收系统已经收集并带引用的证据；提示词明确禁止补造。结构化的 hypothesis、confidence、suggestions 和 evidence 独立持久化，模型只润色摘要。模型异常自动回退规则引擎，高风险变更永远不由模型自动执行。

### 这是 Agent 还是固定流程？

V1.2 的编排阶段是确定性的，工具通过统一接口可插拔，`REPLAN` 根据证据覆盖和失败情况决定结论状态。这样演示时不依赖模型也能复现和测试。启用模型后可以让模型参与计划选择，但工具权限、输入校验、步骤落库和高风险动作边界仍由确定性代码控制。与“让模型自由调用一切”相比，这更适合运维场景。

### 为什么不展示模型的思维链？

平台展示的是系统真实执行记录，不是模型隐藏推理：调用了哪个工具、输入范围是什么、返回了多少证据、耗时和失败原因都可审计。这样既能解释结论，也能被测试和复盘，不会把一段自然语言推理误当成事实。

### 某个工具失败怎么办？

每个工具独立记录 `SUCCEEDED / NO_DATA / FAILED`。单工具失败后继续执行其他只读证据源，最终 run 标为 `PARTIAL` 并降低结论可信度；编排主链路异常才标记 `FAILED`。失败原因写入步骤，但不会把底层异常伪装成无数据。

### 外部 Prometheus 或 Loki 挂了会不会拖垮调查？

Provider 调用有连接和读取超时，单次请求内按配置重试；连续失败达到阈值后打开熔断器，窗口结束只允许一个半开探测。Router 捕获外部失败并切到对应的本地指标或日志 Provider，warning 和实际 Provider 会写进步骤输入。这样能区分“外部观测系统不可用”和“查询没有数据”，也不会让每次调查都等待已知故障的数据源。

### Loki 接入里最容易踩什么坑？

日志历史查询必须使用 `query_range`，开始和结束时间按纳秒传递，日志结果应是 `streams`，并通过 `limit` 与 `direction` 控制数量和顺序。另一个实际问题是 LogQL/PromQL 都包含花括号，直接交给 Spring URI 模板会被误判为变量；当前先构造并编码完整 URI，再发起请求。契约测试覆盖了这个问题，同时验证租户头、Authorization 和响应解析。

### 为什么日志要在工具层脱敏？

日志可能包含 Token、Authorization、邮箱和客户端 IP。如果先写入调查报告再在页面遮挡，敏感值仍会留在数据库和导出文件中。当前在 `LogsProvider` 返回证据前统一脱敏，步骤和报告只接触清洗后的值；生产系统还应在采集端和日志规范上做第一层治理。

### 为什么不把“返回了结果”称作命中率？

返回率只说明检索输出是否非空，不证明相关性。检查点55按持久化查询发生日统计，只把全部返回文档完成独立复核的非空查询和已知空结果纳入质量分母；复核等级≥2至少命中一个文档才计分子。部分正相关、待审、拒绝和历史结果未知单列，零分母显示N/A，并同时给出全量复核覆盖率。K是片段上限，文档评分去重；不是标准去重文档Top-K。晚复核更新原查询日，因此是截至读取时的质量现状而非当日评分历史。实际引擎、来源和K可筛选，原固定集离线分数独立保留；子集存在选择偏差，不能从小样本外推生产质量或把版本前后数字当因果改善。

### 为什么 Runbook 没有直接把 Milvus 接回主链路？

原 OnCall 的链路是 DashScope Embedding、Milvus L2 搜索和可选 `gte-rerank`，但应用启动硬依赖外部服务，索引没有绑定 Runbook 业务版本与 ACL，rerank 失败会中断请求，也没有固定评测。重构后先保留 BM25 基线，再把向量存储隔离成版本绑定索引；只有覆盖完整且 Provider 可用时才进入 Hybrid。当前小语料用数据库 JSON 向量和内存余弦即可验证业务契约，后续规模增长可替换为 Milvus/OpenSearch，而不改变 ACL、融合、降级和评测接口。

### 为什么选择 RRF，而不是直接相加 BM25 分数和余弦相似度？

两种原始分数量纲不同，直接相加依赖脆弱的归一化和权重。RRF 只使用各召回器中的名次，默认按 `1/(60+rank)` 累加；实现简单、结果稳定，也便于说明每条结果的词法名次和向量名次。它是 rank fusion，不等于 cross-encoder rerank；后者仍要在真实标注集上证明收益后才接入。

### 向量索引怎样避免重建失败污染线上检索？

索引内容绑定 `chunkId + contentHash + provider + model`。系统先在数据库事务外分批调用 Embedding，并校验返回数量、统一维度、有限值和非零范数；全部成功后才在短事务里删除旧模型索引并插入新向量。相同内容指纹直接复用；失败运行只记录错误码，旧索引不会被提前删除。即使文档在构建期间发布新版本，覆盖率也会下降并触发 BM25 降级，而不会用残缺向量悄悄回答。

### Runbook 引用怎样避免内容更新后漂移？

业务主键 `stableKey` 表示同一手册，内容变化创建递增的不可变版本；引用同时包含版本号和分块号，例如 `runbook:redis-pool:v2#chunk-1`。旧版本只改为 `SUPERSEDED`，不会被覆盖，因此历史 Agent 报告仍能定位到当时内容。当前分块号在单个版本内稳定，后续跨版本语义对齐需要独立 chunk 标识。

### 检索效果为什么不能只展示几个成功例子？

V1.6 保存固定改写查询及分级 qrels，在同一数据集上重放旧版关键词 contains、BM25 和可用时的 Hybrid，计算 Recall@3、MRR、NDCG@3 与首位稳定引用命中率，并保留失败结果和不可用原因。13 条种子样例中旧版 Recall@3/MRR/NDCG@3 为 0，BM25 Recall@3 为 1、MRR 为 0.961538、NDCG@3 为 0.971610、首位引用为 0.923077。Hybrid 没有真实索引时显示 unavailable，测试替身的结果只证明管线契约，不能包装成模型准确率。

### 为什么已有 Recall 和 MRR，还要加 NDCG？

Recall@3 只回答相关文档有没有进入前三，MRR 只关心第一个相关结果的位置；当同一查询有多个不同相关等级的文档时，两者都无法判断“高度相关是否排在部分相关之前”。NDCG@3 用 `2^grade-1` 放大等级差异，再按排名位置折损，并与理想排序归一化到 0–1。实现按唯一查询聚合多个 qrels；同一 query-document 的重复独立判断取等级均值，避免活跃查询或重复复核被多算权重。

### 怎样避免用户反馈直接污染评测集？

检索响应先绑定不可变结果快照，用户只能评价本人查询中实际返回的文档，不能任意指定 query-document 对。判断采用 0–3 级并先进入 `PENDING`；待办排除本人，且只展示查询与当时结果摘要，不显示原始等级、评论或提交人，减少锚定偏差。复核人必须重新评分，版本号避免并发覆盖；复核等级 ≥ 2 才生成正相关 case，0/1 保留但不转换为预期命中。离线评测走不记录遥测的入口，避免测试查询反向污染数据。

### 为什么用线性加权 Cohen's kappa，而不是只看两人相同率？

精确一致率没有扣除随机一致，也把“3 对 2”和“3 对 0”视为同样错误。当前是两名标注人、0–3 四级序数标签，因此用线性权重 `|i-j|/3` 计算 κ；同时保留精确一致率和相差不超过一级的比例，避免单一指标掩盖实际分歧。没有样本或两边都只使用同一个标签时，期望加权分歧为 0，κ 在数学上未定义，接口返回 `null/N/A`。若未来超过两名标注人或需要争议仲裁，应换用适合多标注人的指标与独立仲裁流程，不能硬套 Cohen's kappa。

### 为什么到期检索快照不直接执行 DELETE？

检索快照已经被判断、复核、审计和离线评测引用，直接物理删除会破坏外键与证据链。当前把查询正文、结果 JSON 和查询人视为有保留期的敏感载荷：到期后改成不可逆墓碑值，未复核判断自动拒绝并清空自由文本，已经独立复核形成的 qrel 因为提前复制了脱敏查询、稳定文档键和等级而继续可用。清理任务按固定批次选择活跃到期数据，重复执行不会再次处理或重复写审计。这里的“擦除”只覆盖在线主库载荷，不冒充数据库备份和导出副本已经同步销毁。

### 为什么 Postmortem 要固化证据快照，而不是每次打开动态查询？

复盘要回答“当时基于什么做出结论”。如果每次打开都动态拼接最新时间线，后加的备注会改写历史依据，审计也无法复现。当前在创建草稿前按时间顺序读取 Incident 时间线，并保存告警、调查报告和变更引用；自由文本先脱敏，之后新增的复盘事件不会反向进入这份快照。代价是快照可能遗漏后来发现的证据，所以草稿正文允许补充，但发布流程会记录明确版本和独立复核人。

### 为什么复盘必须有行动项，而且提交人不能自审？

只有原因描述、没有责任人和期限的复盘很难转化为防复发工作，因此服务端要求至少一个可执行行动项，并限制负责人必须具有运维处置权限。提交人与复核人分离用于减少确认偏差；不能只在前端隐藏按钮，后端还比较用户 ID。复核可以退回修改，发布后正文冻结，但行动项继续独立流转，否则“发布复盘”和“完成整改”会被错误地视为同一件事。

### 为什么 MTTA/MTTM/MTTR 要分别展示样本数和中位数？

三个里程碑的缺失情况不同：未确认事故不能进入 MTTA，未缓解事故不能进入 MTTM，未恢复事故不能进入 MTTR。把缺失值记为 0 会系统性美化指标，强行共用分母也会让指标不可解释。均值便于容量和总体成本判断，中位数降低少量极慢事故的影响，样本数和慢事故明细让使用者知道结论由多少事实支撑。负时长属于数据异常，同样只排除并保留原始 Incident 供下钻，不静默改写源数据。

### 为什么逾期扫描要保存独立事实，而不是每次查询动态算红色？

动态计算只能说明“现在看起来逾期”，无法回答首次何时发现、谁触发、是否重复处理以及完成后何时关闭。系统为每个行动项最多保存一条升级记录，扫描时用行锁和唯一约束防止并发重复，只有首次创建才写时间线和审计，完成事务再关闭这条记录。当前没有真实邮件或企业 IM 连接器，因此这条记录只称为内部升级事实，不冒充消息送达回执。

### 值班升级如何避免双实例重复，又怎样处理缺班？

每次扫描先锁定 Incident，再复核仍为 `OPEN`；数据库对 `(incident_id, step_id)` 建立唯一约束，首次执行才写升级事件、站内通知、时间线和审计。确认流程也更新同一 Incident，因此行锁排序能防止在已经确认后追加步骤；已到期但没执行的步骤可由后续扫描补记，不声称任务或外部通知 exactly-once。无活跃班次/用户时终态记录 `NO_TARGET`，不伪造通知；该步骤不会因后来补班而自动重试，后续 USER/ROLE 步骤仍按时限独立执行。checkpoint 43 增加单次班次维护，checkpoint 45 补轮转后台/API，checkpoint 46 补管理/台账页面；检查点49–51已补定向接班请求及双方页面，完整互换与渠道送达回执仍待建设。

### 接班申请已经发出但响应丢了，刷新后能换一个键吗？

不能把网络错误当作事务未提交。前端在首次发送前保存原UUID与不可变内容，按登录账号分区；发送后冻结，刷新只恢复，手动重试原载荷。服务端以申请人+键唯一且逐项匹配，返回原请求，包括已经决定的终态；不同内容复用同键返回409。sessionStorage只覆盖同一标签页的恢复，不承诺标签页关闭后仍在。明确放弃本地草稿也不撤回服务端请求，必须核对台账。这比单纯禁用按钮更能处理真实不确定提交，且不声称exactly-once网络投递。

### 为什么接班台账不能先取200条，再在浏览器筛选本人？

较旧本人待办会被较新无关记录挤出，页面看起来“没有待办”却只是漏读。计划、本人两种参与身份与状态在SQL内先过滤再截断，MINE从认证主体取ID，不能由调用者指定他人冒充本人范围。筛选后仍超过200条就明确提示不完整。checkpoint50共享H2/MySQL和checkpoint51真实HTTP/browser都用201条新无关请求验证旧待办仍可见，而不是只用空列表证明筛选可用。

### 为什么管理员不能代替别人接受接班，而409后不能自动刷新版本重提？

接班改变的是指定人员的责任，管理权限不等于本人同意；当前设计只让源负责人申请、目标本人接受/拒绝、申请人撤回。接受在计划/请求/人员行锁中重查版本、资格、时间与重叠，并同事务生成覆盖和审计，原班次、旧事故路由不改写。旧版本409说明用户审阅的事实已变化，自动替换版本会把乐观锁变成无意义参数；前端锁定旧决定，要求重新核对选择。页面按钮不是安全边界，最终规则在服务端；双向互换、开放认领与外部送达仍未完成。

### 已经接受接班，后来撤销为什么不能把状态改为WITHDRAWN？

接受是接班人当时的同意事实，WITHDRAWN是申请人在待处理阶段撤回，混用会抹掉责任变更历史。V28独立记录管理撤销人/时间/说明/捕获版本与操作键，覆盖行软取消，原ACCEPTED记录与旧路由不变；原班次或计划也可能已停用，不能一概说撤销后原负责人自动接续。UI分别展示原决定、实际覆盖和独立撤销；普通维护取消没有这条意图记录时也明确说明，不虚构账本。

### 撤销已提交但响应丢失，怎样避免换版本、换键重复操作？

首次POST前把管理人、请求ID、双版本、UUID和说明按账号保存到版本化sessionStorage；存储失败不发送，之后冻结。刷新GET只核对实际事实，不自动POST或更新捕获版本，管理人按需手动重试原意图。服务端唯一键和逐项匹配返回原撤销事实；409/403锁定意图，锁定也跨刷新保留，明确放弃只清本地草稿，不恢复服务器覆盖。checkpoint54真实浏览器以200提交后丢响应、班次竞争取消409、存储失败零POST和手机日历自动刷新验证；不宣传跨标签页/跨设备恢复或网络exactly-once，远端结果以验收报告为准。

### 为什么MySQL断言全绿还要检查完整停机日志？

检查点51实际遇到52项断言通过、BUILD SUCCESS，但JUnit按类停止MySQL容器后，Spring缓存上下文中的恢复任务仍继续查询旧连接池；出现六次后台连接异常和Surefire强制fork退出。业务断言只证明当时请求结果，不能证明资源释放、后台任务或下一轮隔离正确。检查点52将独立容器交给Spring管理，令数据库活到依赖它的Bean销毁之后，并用完整Maven日志、五连接池关闭和五套零跳过报告作额外门禁。补正276b57b的Run36329512979已验证52项零跳过、五池完整关闭与完整日志门禁通过；不通过关闭任务、降低日志级别或只扫描测试总计之前的日志来制造绿色。

### 为什么取消班次要保留记录，而且不能只在浏览器检查重叠？

取消会改变谁承担值班职责，需要保留原时段、取消时间、理由、版本与审计，不能 DELETE 后失去事实。创建/取消先锁同一个计划行，串行化相互冲突的写入；重叠检查用锁定读避免 MySQL 旧快照，同层不能重叠，但普通和临时覆盖可并存，边界 `[开始, 结束)` 能交接。H2 双线程及真实 MySQL 条件用例验证一个成功、另一个 409；实际 MySQL 是否通过以最新报告为准。当前路由排除取消行，取消覆盖恢复普通班次，但不修改历史升级接收人。前端只是提示与带版本提交，最终约束在服务端。

### 为什么轮转要物化、留来源账本，而不是每次临时算值班人？

临时计算很难区分手工排班、自动生成、冲突和有意取消。规则用锚点与时段序号决定成员，物化到已有普通班次，并用轮转/时段来源唯一键防重；与手工班冲突就留受阻台账，不覆盖，已经生成再取消的时段也不复活。暂停仅停止续排，已生成班次仍是明确事实。每条规则独立事务，一条失败回滚而其他规则继续。账号停用/职责撤销不改历史接收人，但当前资格另行反馈并排除新路由。checkpoint 46 页面已展示有序创建、异常/取消与版本竞争，当前仍限固定数据库时钟，定向接班已由49–51补齐，多时区和完整互换仍待补，不能宣传为完整的全球排班产品。

### 为什么取消已提交，旧调查仍可能通知原值班人？

这是事务快照而非前端刷新问题：MySQL 默认 REPEATABLE_READ 中，接入的 CMDB 读取或扫描的候选查询会建立旧快照；之后再用普通查询读班次，可能仍见到已被另一事务取消的覆盖。checkpoint 44 用实际接入/扫描入口和提交闸门先复现，再显式 READ_COMMITTED，让每次相关读取可见此前已提交的变动。没有拆开告警与通知事务，失败时六类事实一起回滚；Incident 锁和步骤唯一约束仍负责防重。保证止于“对应查询前已提交”，查询后才取消不会撤回历史路由；已有外层事务也必须遵循此隔离契约。真实 MySQL 证据以本检查点报告为准，不把 H2 通过冒充 MySQL 已验。

### 为什么 UTC CI 能暴露本机没有发现的时间错误？

上海本机上应用时间与数据库时间看起来一致；换到 UTC 后，硬编码上海的创建/聚合时间与数据库默认的确认时间相差八小时，会导致漏聚合甚至负 MTTA。修复不是改测试预期，而是让事故创建、聚合窗口、当前班次和默认升级扫描使用数据库会话时钟，并保留旧 Problem Management 断言、增加“确认不早于创建”的真实接口回归。两种时区全量测试和真实 MySQL 门禁只证明当前模型的一致性，不等于已经支持多时区排班。

### 重复事故为什么先用精确指纹，而不是直接宣传 AI 相似聚类？

当前数据没有人工确认的相似事故标签，也没有足够样本校准阈值。直接上向量并展示一个百分比，无法证明召回的是同一故障模式，反而容易把同一服务的不同问题误合并。本轮先以“归属服务 + SHA-256 告警指纹 + 不同 Incident”为高精度基线，并同时展示匹配原因、事故数、日期数、时间跨度和告警 occurrence。它召回率有限，但每个候选都能用数据库事实解释；后续语义聚类必须和这条基线在脱敏历史标注集上比较 Precision/Recall，再决定是否进入主流程。

### Problem 已解决后同类 Incident 再出现，为什么不自动重开？

“出现相同指纹”证明的是信号复发，不等于原根因和修复一定失效，也可能是监控规则复用、回滚或新的触发条件。系统会自动幂等关联新 Incident 并标记 `recurredAfterResolution=true`，但保留 Problem 的 `RESOLVED`，由负责人审阅新证据后显式重开。这样自动化负责收集事实，人负责改变治理结论；状态变更仍受乐观锁、权限和审计保护。

### 两名经理同时把候选登记为 Problem，怎样避免重复？

先查再插只能优化常见路径，不能消除竞态。最终一致性由数据库 `recurrence_key` 唯一约束保证：一个事务成功创建，另一个捕获唯一键冲突后回读同一 Problem，再用 `problem_id + incident_id` 唯一约束补齐缺失关联。MySQL 默认 REPEATABLE READ 下，失败者先前的普通查询已经建立旧快照；第一次修复只把主键查询改成 `SELECT ... FOR UPDATE`，远端真实 MySQL 随即证明后续关联同步中的普通查询仍看不到赢家。因此最终把赢家回收、关联同步和视图读取整体放进 `REQUIRES_NEW` 新事务，而不是只修一个查询。测试让两个事务先各自确认记录不存在，再同时创建，验证恰好一个 `created=true`、两个响应主键相同，并且关联与时间线不重复；等待均设上限，避免死锁被误当成通过。

### SQL 注入怎么防？

业务参数全部通过 `JdbcClient` 命名参数绑定，不拼接用户输入。仅筛选条件的固定 SQL 片段由代码控制；排序规则也固定在服务端。前端输入不能进入 SQL 结构位置。

### JWT 为什么每次还查用户？

纯粹信任 Token 会导致账号停用后仍能使用到过期。过滤器验签后重新加载用户状态和角色，牺牲一次轻量查询换取及时失效；规模增长后可用短期缓存并在账号变更时主动失效。

### H2 和 MySQL 会不会不一致？

H2 用于本地零配置和快速回归，并启用 MySQL 兼容模式，但不把兼容模式当成真实数据库证明。Testcontainers 会启动 MySQL 8.4，从空库执行 Flyway V1-V15，并验证中文种子数据、幂等复合唯一索引、Runbook 检索、快照生命周期、完整调查链路、复盘发布、逾期扫描、行动项关闭和 Problem 状态闭环；GitHub Actions 把它作为独立门禁。真实测试曾直接发现缺少 `flyway-mysql` 模块，这正是双数据库验证的价值。若宿主机 Docker 不可用，只能把 H2 结果作为快速回归，不能替代已经取得或远端 runner 产生的 MySQL 通过证据。

### 为什么调查置信度是规则值？

V1 的置信度表达证据强弱分级，不宣称统计学概率。近期相关变更 + 同时出现的依赖告警比只有症状证据更强。后续可基于历史复盘标签做校准，但不能把模型自报置信度当成真实概率。

### 为什么同时保留调查报告和对话？

调查报告是某个时间点的正式证据快照，字段固定、可审计；对话用于值班人员围绕同一上下文继续追问。聊天回答不会覆盖报告，也不能直接流转 Incident。这样既保留 Agent 的交互价值，又不会让非结构化聊天成为业务事实来源。

### SSE 流式对话怎样保证安全？

入口是携带 JWT 的 POST 请求，服务端先校验会话归属再生成回答。Spring MVC 的 `SseEmitter` 会触发异步 dispatcher，因此只放行内部 `ASYNC/ERROR` 分派，首次请求仍必须鉴权。事件分成 `meta/delta/done/error`，完整消息落库后才发送，断线后可以从会话历史恢复。

### Agent SSE 和对话 SSE 有什么不同？

Agent 调查事件是执行过程中逐步产生的真实事件，先写 `agent_investigation_event` 再发送，SSE `id` 就是数据库事件 ID，客户端可用 `after` 游标补齐断线期间的事件。对话当前先生成并保存完整回答，再按 `meta/delta/done` 协议分块发送；它能恢复历史消息，但还不是模型 Provider 原生 token 流。这两个能力不混为一谈。

### 为什么客户端断开后不取消 Agent 调查？

调查结果属于 Incident 证据，不应因某个浏览器关闭就消失。服务端只停止向已断开的 emitter 发送，后台任务继续完成 run、报告、时间线和审计；用户重新进入后通过 run 详情和事件回放恢复。业务取消使用独立 API，记录取消人、原因和时间，并中断受管任务，因此网络断开和显式取消有清晰不同的语义。

### 事件已经落库，为什么还需要消息队列？

数据库事件 ID 负责顺序、回放和审计，但不会立即唤醒持有 SSE 的其他实例。因此事件与 outbox 同事务落库，Redis Streams 只传 `runId/eventId` 通知，每个实例独立读取；通知重复、乱序或丢失时，订阅端仍以数据库游标补读。这是 at-least-once 通知加幂等消费，不声称 exactly-once。

### 执行 Agent 的 JVM 被杀后，其他实例会续跑吗？

不会自动续跑。事件分发与任务迁移是两个问题：B 可以回放 A 已提交的事件，但没有 A 内存中的工具调用栈。OpsPilot 把绝对 deadline 持久化，存活实例扫描逾期活动 run，在行锁内重检并只结算一次 `TIMED_OUT / CANCELLED`，同时写终态事件、时间线和审计。六个工具都是只读，所以当前选择“明确失败并人工重试”，而不是在无执行租约/fencing token 时冒险重放。

### Agent 进入异步线程池后，Trace 为什么不会断？

HTTP 线程在把任务交给有界执行器前捕获当前 Micrometer `Span`，worker 在该 span scope 内创建 `opspilot.agent.run`，然后工具和 Provider 逐层成为子 span。OpenTelemetry span 结束后其 context 仍可作为后续父上下文，所以 HTTP 响应先返回也能保持 traceId。SDK 测试专门在根 span 结束后才启动 worker 并断言四层 ID；独立容器门禁再把真实调查经 Collector 写入 Tempo，用 TraceQL 按 run ID 找回并经 Grafana 数据源代理读回。故障场景中 Tempo 在调查期间被停止，调查仍完成且应用健康，Collector 观察到连接拒绝并在 Tempo 重启后完成导出。Prometheus/Loki 不能直接调用 `RestClient.builder()`，否则绕过 Boot 的观测定制器；现在注入自动配置 builder。checkpoint-24 协议测试证明两个下游收到 W3C `traceparent` 且 header spanId 对应导出的 HTTP client span；checkpoint-25 又用独立 JVM 验证两个服务在同一 Tempo trace 中严格形成 `provider.query -> CLIENT -> SERVER`，正常和短暂停机恢复均为两条完整分支。无当前 span 时不强行 scope `null`，run 作为新根。61/62已补同卷SIGKILL/新容器及默认十消费者恢复；真实生产 Prometheus/Loki 集群、生产采样、磁盘/卷故障与生产容量仍需独立验收。

### 高风险处置为什么禁止发起人自批？

Agent 结论和发起操作可能共享同一个人的判断，独立审批可以降低确认偏差和误操作风险。服务端比较 `requested_by` 与当前审批人，不能只依赖前端隐藏按钮；审批更新还带版本号和待审批状态，避免两名审批人同时覆盖。批准、拒绝都会写入时间线和审计日志。

### 为什么批准后仍不自动执行回滚？

审批闭环和生产执行是两个风险等级。V1.4 先把建议、证据、权限、双人原则和并发控制做实；真正执行还需要凭证隔离、目标环境校验、幂等、回滚验证、超时和执行器审计。当前 `APPROVED` 只表示治理门禁通过，诚实保留这个边界比用模拟按钮宣称自动修复更可靠。

### Runbook为什么不能导入后立即供Agent检索？

导入者可能提交错误恢复步骤或扩大ACL；立即发布会直接改变调查证据。V30先创建不可变待审候选，绑定正文、来源、元数据、ACL、提交人与当时发布基线，另一当前管理账号批准才进入BM25/Agent/已发布向量集合。审批和替换旧版本、审核事实、审计同事务；拒绝或本人撤回不影响旧发布版。独立审批降低治理风险，但不能声称证明手册事实正确或消除提示注入。

### 文档版本、审核版本、发布基线和幂等键分别防什么？

文档版本标识不可变内容；审核版本防止旧决定覆盖已改变的候选状态；发布基线阻止两个独立候选先后批准时较旧候选覆盖后来发布版；幂等键与ID/操作者/原审核版本/决定/原始说明哈希绑定，区分精确重放和同键不同意图。已SUPERSEDED的批准重放只读现状，不复活旧版。稳定键行锁串行化发布，原子upsert避免重复INSERT共享锁升级竞态，回包使用当前读而不是MySQL旧快照。H2与实际MySQL的双独立事务、外层回滚和迁移保留历史共同验证，具体代码SHA/范围见[checkpoint56](acceptance/V1.7-checkpoint-56.md)。

### 为什么刷新、网络失败和本地放弃不能悄悄重提审批？

响应丢失不等于服务端没有提交。首POST前按账号保存冻结ID/版本/键/决定/说明；刷新只GET，手动重试逐字使用同键。403/409锁定旧意图而不是自动换版本；损坏存储保留原文并阻断新提交，配额失败零POST，详情404仍允许明确放弃。本地放弃不是服务端撤回，跨账号不能恢复他人意图。真实UI通过故意丢响应、刷新重放与旧基线冲突验证；浏览器会话恢复不冒充跨设备租约或exactly-once执行。

## 可诚实说明的不足

- 当前通知通道是站内记录，未接真实企业微信/短信回执。
- 告警接入是同步 REST，尚未用 Kafka 承担突发流量。
- Alertmanager 已有标准 v4 入站 webhook：独立密钥、批量上限、逐项永久错误隔离，以及 `fingerprint + startsAt` 生命周期幂等；相同状态重试零写入，resolved 更新同一告警并留时间线。永久坏项使用 `fingerprint + startsAt + status` 的脱敏持久台账，管理/值班角色可用短租约重放，AUDITOR 只读；原告警外部 ID 是第二层幂等保障。它仍是同步 receiver，尚无自动退避/保留期、真实大批量压测，也不代表 SLO 已向 Alertmanager 出站通知或获得渠道回执。
- 数据权限做到角色级，尚未细化到部门和资源范围。
- Runbook 已具备可选 Embedding、持久化向量、RRF、盲化双评分、线性加权 κ、分级 NDCG，以及主库快照写前脱敏与定时保留期擦除，但默认未启用真实 Provider；13 条仍是种子集，隔离 QA 的双评分也不是历史生产标注，未证明真实 Embedding 或 cross-encoder rerank 优于 BM25。当前一致性只支持两名标注人且没有第三方仲裁；快照治理尚未覆盖备份/导出副本、按租户差异化策略和用户级删除请求，当前向量查询为内存全量余弦，不适合大语料；PDF 只支持可提取文本，不做 OCR。
- AI 模式需要外部 DashScope Key，默认演示采用规则引擎。
- 已提供 Prometheus 与 Loki HTTP 适配器，但默认演示关闭外部依赖；当前通过协议级本地 HTTP 契约测试验证，尚未与真实生产集群联调和压测。
- OpenTelemetry 业务 span、异步上下文和真实 SDK exporter 契约已验证；可选 Compose 已包含 Collector、Tempo 和 Grafana，正常读回、Tempo 短暂停机恢复、W3C 出站传播及独立 fixture 的跨 JVM CLIENT/SERVER 拼接均已验证。61/62已验证同卷SIGKILL/新容器恢复及默认十消费者；仍未与真实生产 Prometheus/Loki 集群联调，也未验证生产采样成本、对象存储保留、磁盘/卷故障和生产容量。
- Agent 步骤已经使用持久化实时 SSE 和游标回放；对话仍是完整回答落库后的协议分块，尚未做到模型 Provider 原生 token 流。
- Agent 事件已通过 outbox + Redis Streams + 数据库补读支持跨实例广播，崩溃孤儿 run 可在持久化 deadline 后收敛到终态；但工具链仍不会跨节点续跑，也没有执行租约/fencing token 或 exactly-once 保证。
- 处置审批已完成治理闭环，但尚未接 Argo CD、Ansible、Kubernetes 等生产执行器。
- Postmortem 已覆盖证据快照、独立发布、行动项责任闭环、跨 Incident 待办、逾期事实和 MTTA/MTTM/MTTR；Problem 已覆盖精确指纹复发；服务 SLO 已按 Prometheus 好事件/总事件计算错误预算，并用三档长/短窗口燃烧率区分 PAGE 与工单信号；Alertmanager 入站生命周期已经闭环。Runbook真实持久化查询趋势已区分返回率、独立复核覆盖、可计分子集Hit@K与未知，但不等于长期生产准确率。仍缺真实企业渠道/人工回执、跨 Incident 语义相似/依赖共因聚类、生产 recording rules、低流量样本策略与Alertmanager出站通知；独立fixture接收器不能冒充企业渠道。
