# OpsPilot 面试讲解与追问

## 30 秒项目介绍

> OpsPilot 是我把原 OnCall AI Agent 重构成的企业级故障闭环平台。它先对 Prometheus/APM 告警去重聚合，再结合 CMDB 形成 Incident，通过状态机、值班升级和审计完成闭环。调查部分采用可解释 Agent 工作流，按计划调用告警、拓扑、指标、变更、日志和 Runbook 六个只读工具；真实检索快照写前脱敏，并通过盲化双评分和 NDCG 形成可复现评测。步骤和实时事件先落库，再通过 SSE 推送并支持游标回放。事故恢复后从真实证据生成无责复盘，必须补全影响、原因和经验并绑定负责人/期限行动项，提交人不能自审，发布后正文冻结；运营页再按独立样本口径展示 MTTA/MTTM/MTTR，并对跨事故逾期行动项形成幂等、可关闭的升级事实。高置信度变更关联也只生成回滚草案，系统不会直接修改生产环境。

## 简历项目描述

**OpsPilot 企业级智能运维与故障闭环平台**

- 设计告警与 Incident 分层模型，通过外部事件 ID、SHA-256 指纹和时间窗口实现重复告警压缩，并结合 CMDB 服务关系自动聚合事故。
- 实现受限状态机、乐观锁和全量时间线，解决多人值班协同时的非法跳转与更新覆盖问题；使用 JWT、RBAC、BCrypt 和审计日志控制关键操作。
- 设计可解释 Agent 调查编排，以 `PLAN-EXECUTE-REPLAN-FINISH` 驱动 6 个可插拔只读工具；持久化 Provider、查询范围、状态、证据引用、失败原因与耗时，支持单工具故障隔离和 `PARTIAL` 降级。
- 实现“事件先落库、再 SSE 推送”的调查流；一次成功调查产生 18 条有序事件，并以数据库事件 ID 支持断线游标回放；使用有界线程池隔离异步任务，客户端断开不丢失后台调查结果。
- 抽象 Metrics/Logs Provider SPI，实现 Prometheus instant query、Loki range query 与本地证据适配；支持 Loki 多租户/Token、结构化日志解析，并通过超时、重试、跨请求熔断、本地降级和敏感字段脱敏提升外部观测系统异常时的调查可用性。
- 构建证据报告链路，自动关联告警、拓扑、指标、日志、故障窗口变更和 Runbook；支持离线规则结论及 DashScope 受约束摘要，模型不可用时自动降级。
- 实现版本化 Runbook 知识库：Markdown/PDF 入库、内容哈希幂等、不可变版本、角色 ACL 与标题分块；构建模型版本绑定的持久化向量索引，以 RRF 融合 BM25/向量名次，并在索引残缺或 Provider 故障时显式降级。13 条固定种子集按引擎保存 Recall@3、MRR、NDCG@3、引用命中率、失败样例和 unavailable 原因。
- 构建检索反馈治理闭环：真实查询和结果写库前统一脱敏，快照按可配置保留期批量擦除敏感载荷并记录审计；限制用户只能标注本人看到的文档，复核接口隐藏原始评分和提交人，以第二个 0–3 级评分形成最终 qrel，并计算精确一致率与线性加权 Cohen's kappa；清理后仍保留已复核的结构化评测样本。
- 设计高风险处置治理门禁：Agent 仅生成带证据的回滚草案，RBAC 限制审批角色，禁止申请人自批，并通过版本号乐观锁、时间线和审计日志保证审批可追溯且不被并发覆盖。
- 实现证据驱动的无责事故复盘：恢复后固化脱敏时间线、告警/调查/变更引用，五类正文与防复发行动项作为提交门禁，提交人与发布人分离；父子乐观锁、发布冻结和责任人完成留痕覆盖 H2/MySQL 8.4。
- 构建事故运营指标与行动项治理：按日期/严重等级统计 MTTA/MTTM/MTTR 均值、中位数和独立样本数，排除缺失/负时长并下钻慢事故；跨 Incident 筛选负责人待办，以唯一升级记录、行锁和定时扫描保证逾期处理幂等，完成后保留并关闭历史事实。

## 高频追问

### 为什么 Alert 和 Incident 要分开？

Alert 是监控规则产生的观测事件，可能重复、抖动或来自同一故障的不同指标；Incident 是需要人负责、流转和复盘的业务事故。一对多建模后才能保留原始证据，同时避免值班人员处理几十条重复任务。

### 指纹为什么不用标题直接做唯一键？

同一个标题可能发生在不同服务和严重等级，且同一告警在恢复后再次触发应创建新事件。指纹包含来源、资源、等级和规范化标题，再配合活跃状态与 30 分钟窗口判断，不将所有历史告警永久合并。

### 并发流转怎么处理？

客户端读取 `version`，更新 SQL 使用 `WHERE id=? AND version=?` 并执行 `version=version+1`。受影响行数为 0 表示其他人先更新，返回 409 让客户端刷新。这样避免最后写入者静默覆盖前一个人的处置结果。

### 为什么不用微服务？

当前模块规模和团队规模不需要承担分布式事务、服务发现和链路排障成本。先用模块化单体明确领域边界；告警吞吐和通知可靠性真正成为瓶颈后，再拆 Alert Intake、Notification，并通过事件消息解耦。

### AI 怎样避免幻觉？

模型不拥有数据查询自由，只接收系统已经收集并带引用的证据；提示词明确禁止补造。结构化的 hypothesis、confidence、suggestions 和 evidence 独立持久化，模型只润色摘要。模型异常自动回退规则引擎，高风险变更永远不由模型自动执行。

### 这是 Agent 还是固定流程？

V1.2 的编排阶段是确定性的，工具通过统一接口可插拔，`REPLAN` 根据证据覆盖和失败情况决定结论状态。这样演示时不依赖模型也能复现和测试。启用模型后可以让模型参与计划选择，但工具权限、输入校验、步骤落库和高风险动作边界仍由确定性代码控制。与“让模型自由调用一切”相比，这更适合运维场景。

### 为什么不展示模型的思维链？

平台展示的是系统真实执行记录，不是模型隐藏推理：调用了哪个工具、输入范围是什么、返回了多少证据、耗时和失败原因都可审计。这样既能解释结论，也能被测试和复盘，不会把一段自然语言推理误当成事实。

### 某个工具失败怎么办？

每个工具独立记录 `SUCCEEDED / NO_DATA / FAILED`。单工具失败后继续执行其他只读证据源，最终 run 标为 `PARTIAL` 并降低结论可信度；编排主链路异常才标记 `FAILED`。失败原因写入步骤，但不会把底层异常伪装成无数据。

### 外部 Prometheus 或 Loki 挂了会不会拖垮调查？

Provider 调用有连接和读取超时，单次请求内按配置重试；连续失败达到阈值后打开熔断器，窗口结束只允许一个半开探测。Router 捕获外部失败并切到对应的本地指标或日志 Provider，warning 和实际 Provider 会写进步骤输入。这样能区分“外部观测系统不可用”和“查询没有数据”，也不会让每次调查都等待已知故障的数据源。

### Loki 接入里最容易踩什么坑？

日志历史查询必须使用 `query_range`，开始和结束时间按纳秒传递，日志结果应是 `streams`，并通过 `limit` 与 `direction` 控制数量和顺序。另一个实际问题是 LogQL/PromQL 都包含花括号，直接交给 Spring URI 模板会被误判为变量；当前先构造并编码完整 URI，再发起请求。契约测试覆盖了这个问题，同时验证租户头、Authorization 和响应解析。

### 为什么日志要在工具层脱敏？

日志可能包含 Token、Authorization、邮箱和客户端 IP。如果先写入调查报告再在页面遮挡，敏感值仍会留在数据库和导出文件中。当前在 `LogsProvider` 返回证据前统一脱敏，步骤和报告只接触清洗后的值；生产系统还应在采集端和日志规范上做第一层治理。

### 为什么 Runbook 没有直接把 Milvus 接回主链路？

原 OnCall 的链路是 DashScope Embedding、Milvus L2 搜索和可选 `gte-rerank`，但应用启动硬依赖外部服务，索引没有绑定 Runbook 业务版本与 ACL，rerank 失败会中断请求，也没有固定评测。重构后先保留 BM25 基线，再把向量存储隔离成版本绑定索引；只有覆盖完整且 Provider 可用时才进入 Hybrid。当前小语料用数据库 JSON 向量和内存余弦即可验证业务契约，后续规模增长可替换为 Milvus/OpenSearch，而不改变 ACL、融合、降级和评测接口。

### 为什么选择 RRF，而不是直接相加 BM25 分数和余弦相似度？

两种原始分数量纲不同，直接相加依赖脆弱的归一化和权重。RRF 只使用各召回器中的名次，默认按 `1/(60+rank)` 累加；实现简单、结果稳定，也便于说明每条结果的词法名次和向量名次。它是 rank fusion，不等于 cross-encoder rerank；后者仍要在真实标注集上证明收益后才接入。

### 向量索引怎样避免重建失败污染线上检索？

索引内容绑定 `chunkId + contentHash + provider + model`。系统先在数据库事务外分批调用 Embedding，并校验返回数量、统一维度、有限值和非零范数；全部成功后才在短事务里删除旧模型索引并插入新向量。相同内容指纹直接复用；失败运行只记录错误码，旧索引不会被提前删除。即使文档在构建期间发布新版本，覆盖率也会下降并触发 BM25 降级，而不会用残缺向量悄悄回答。

### Runbook 引用怎样避免内容更新后漂移？

业务主键 `stableKey` 表示同一手册，内容变化创建递增的不可变版本；引用同时包含版本号和分块号，例如 `runbook:redis-pool:v2#chunk-1`。旧版本只改为 `SUPERSEDED`，不会被覆盖，因此历史 Agent 报告仍能定位到当时内容。当前分块号在单个版本内稳定，后续跨版本语义对齐需要独立 chunk 标识。

### 检索效果为什么不能只展示几个成功例子？

V1.6 保存固定改写查询及分级 qrels，在同一数据集上重放旧版关键词 contains、BM25 和可用时的 Hybrid，计算 Recall@3、MRR、NDCG@3 与首位稳定引用命中率，并保留失败结果和不可用原因。13 条种子样例中旧版 Recall@3/MRR/NDCG@3 为 0，BM25 Recall@3 为 1、MRR 为 0.961538、NDCG@3 为 0.971610、首位引用为 0.923077。Hybrid 没有真实索引时显示 unavailable，测试替身的结果只证明管线契约，不能包装成模型准确率。

### 为什么已有 Recall 和 MRR，还要加 NDCG？

Recall@3 只回答相关文档有没有进入前三，MRR 只关心第一个相关结果的位置；当同一查询有多个不同相关等级的文档时，两者都无法判断“高度相关是否排在部分相关之前”。NDCG@3 用 `2^grade-1` 放大等级差异，再按排名位置折损，并与理想排序归一化到 0–1。实现按唯一查询聚合多个 qrels；同一 query-document 的重复独立判断取等级均值，避免活跃查询或重复复核被多算权重。

### 怎样避免用户反馈直接污染评测集？

检索响应先绑定不可变结果快照，用户只能评价本人查询中实际返回的文档，不能任意指定 query-document 对。判断采用 0–3 级并先进入 `PENDING`；待办排除本人，且只展示查询与当时结果摘要，不显示原始等级、评论或提交人，减少锚定偏差。复核人必须重新评分，版本号避免并发覆盖；复核等级 ≥ 2 才生成正相关 case，0/1 保留但不转换为预期命中。离线评测走不记录遥测的入口，避免测试查询反向污染数据。

### 为什么用线性加权 Cohen's kappa，而不是只看两人相同率？

精确一致率没有扣除随机一致，也把“3 对 2”和“3 对 0”视为同样错误。当前是两名标注人、0–3 四级序数标签，因此用线性权重 `|i-j|/3` 计算 κ；同时保留精确一致率和相差不超过一级的比例，避免单一指标掩盖实际分歧。没有样本或两边都只使用同一个标签时，期望加权分歧为 0，κ 在数学上未定义，接口返回 `null/N/A`。若未来超过两名标注人或需要争议仲裁，应换用适合多标注人的指标与独立仲裁流程，不能硬套 Cohen's kappa。

### 为什么到期检索快照不直接执行 DELETE？

检索快照已经被判断、复核、审计和离线评测引用，直接物理删除会破坏外键与证据链。当前把查询正文、结果 JSON 和查询人视为有保留期的敏感载荷：到期后改成不可逆墓碑值，未复核判断自动拒绝并清空自由文本，已经独立复核形成的 qrel 因为提前复制了脱敏查询、稳定文档键和等级而继续可用。清理任务按固定批次选择活跃到期数据，重复执行不会再次处理或重复写审计。这里的“擦除”只覆盖在线主库载荷，不冒充数据库备份和导出副本已经同步销毁。

### 为什么 Postmortem 要固化证据快照，而不是每次打开动态查询？

复盘要回答“当时基于什么做出结论”。如果每次打开都动态拼接最新时间线，后加的备注会改写历史依据，审计也无法复现。当前在创建草稿前按时间顺序读取 Incident 时间线，并保存告警、调查报告和变更引用；自由文本先脱敏，之后新增的复盘事件不会反向进入这份快照。代价是快照可能遗漏后来发现的证据，所以草稿正文允许补充，但发布流程会记录明确版本和独立复核人。

### 为什么复盘必须有行动项，而且提交人不能自审？

只有原因描述、没有责任人和期限的复盘很难转化为防复发工作，因此服务端要求至少一个可执行行动项，并限制负责人必须具有运维处置权限。提交人与复核人分离用于减少确认偏差；不能只在前端隐藏按钮，后端还比较用户 ID。复核可以退回修改，发布后正文冻结，但行动项继续独立流转，否则“发布复盘”和“完成整改”会被错误地视为同一件事。

### 为什么 MTTA/MTTM/MTTR 要分别展示样本数和中位数？

三个里程碑的缺失情况不同：未确认事故不能进入 MTTA，未缓解事故不能进入 MTTM，未恢复事故不能进入 MTTR。把缺失值记为 0 会系统性美化指标，强行共用分母也会让指标不可解释。均值便于容量和总体成本判断，中位数降低少量极慢事故的影响，样本数和慢事故明细让使用者知道结论由多少事实支撑。负时长属于数据异常，同样只排除并保留原始 Incident 供下钻，不静默改写源数据。

### 为什么逾期扫描要保存独立事实，而不是每次查询动态算红色？

动态计算只能说明“现在看起来逾期”，无法回答首次何时发现、谁触发、是否重复处理以及完成后何时关闭。系统为每个行动项最多保存一条升级记录，扫描时用行锁和唯一约束防止并发重复，只有首次创建才写时间线和审计，完成事务再关闭这条记录。当前没有真实邮件或企业 IM 连接器，因此这条记录只称为内部升级事实，不冒充消息送达回执。

### 重复事故为什么先用精确指纹，而不是直接宣传 AI 相似聚类？

当前数据没有人工确认的相似事故标签，也没有足够样本校准阈值。直接上向量并展示一个百分比，无法证明召回的是同一故障模式，反而容易把同一服务的不同问题误合并。本轮先以“归属服务 + SHA-256 告警指纹 + 不同 Incident”为高精度基线，并同时展示匹配原因、事故数、日期数、时间跨度和告警 occurrence。它召回率有限，但每个候选都能用数据库事实解释；后续语义聚类必须和这条基线在脱敏历史标注集上比较 Precision/Recall，再决定是否进入主流程。

### Problem 已解决后同类 Incident 再出现，为什么不自动重开？

“出现相同指纹”证明的是信号复发，不等于原根因和修复一定失效，也可能是监控规则复用、回滚或新的触发条件。系统会自动幂等关联新 Incident 并标记 `recurredAfterResolution=true`，但保留 Problem 的 `RESOLVED`，由负责人审阅新证据后显式重开。这样自动化负责收集事实，人负责改变治理结论；状态变更仍受乐观锁、权限和审计保护。

### 两名经理同时把候选登记为 Problem，怎样避免重复？

先查再插只能优化常见路径，不能消除竞态。最终一致性由数据库 `recurrence_key` 唯一约束保证：一个事务成功创建，另一个捕获唯一键冲突后回读同一 Problem，再用 `problem_id + incident_id` 唯一约束补齐缺失关联。双线程集成测试从同一闸门同时发起创建，验证恰好一个 `created=true`、两个响应主键相同，并且关联与时间线不重复。

### SQL 注入怎么防？

业务参数全部通过 `JdbcClient` 命名参数绑定，不拼接用户输入。仅筛选条件的固定 SQL 片段由代码控制；排序规则也固定在服务端。前端输入不能进入 SQL 结构位置。

### JWT 为什么每次还查用户？

纯粹信任 Token 会导致账号停用后仍能使用到过期。过滤器验签后重新加载用户状态和角色，牺牲一次轻量查询换取及时失效；规模增长后可用短期缓存并在账号变更时主动失效。

### H2 和 MySQL 会不会不一致？

H2 用于本地零配置和快速回归，并启用 MySQL 兼容模式，但不把兼容模式当成真实数据库证明。Testcontainers 会启动 MySQL 8.4，从空库执行 Flyway V1-V15，并验证中文种子数据、幂等复合唯一索引、Runbook 检索、快照生命周期、完整调查链路、复盘发布、逾期扫描、行动项关闭和 Problem 状态闭环；GitHub Actions 把它作为独立门禁。真实测试曾直接发现缺少 `flyway-mysql` 模块，这正是双数据库验证的价值。若宿主机 Docker 不可用，只能把 H2 结果作为快速回归，不能替代已经取得或远端 runner 产生的 MySQL 通过证据。

### 为什么调查置信度是规则值？

V1 的置信度表达证据强弱分级，不宣称统计学概率。近期相关变更 + 同时出现的依赖告警比只有症状证据更强。后续可基于历史复盘标签做校准，但不能把模型自报置信度当成真实概率。

### 为什么同时保留调查报告和对话？

调查报告是某个时间点的正式证据快照，字段固定、可审计；对话用于值班人员围绕同一上下文继续追问。聊天回答不会覆盖报告，也不能直接流转 Incident。这样既保留 Agent 的交互价值，又不会让非结构化聊天成为业务事实来源。

### SSE 流式对话怎样保证安全？

入口是携带 JWT 的 POST 请求，服务端先校验会话归属再生成回答。Spring MVC 的 `SseEmitter` 会触发异步 dispatcher，因此只放行内部 `ASYNC/ERROR` 分派，首次请求仍必须鉴权。事件分成 `meta/delta/done/error`，完整消息落库后才发送，断线后可以从会话历史恢复。

### Agent SSE 和对话 SSE 有什么不同？

Agent 调查事件是执行过程中逐步产生的真实事件，先写 `agent_investigation_event` 再发送，SSE `id` 就是数据库事件 ID，客户端可用 `after` 游标补齐断线期间的事件。对话当前先生成并保存完整回答，再按 `meta/delta/done` 协议分块发送；它能恢复历史消息，但还不是模型 Provider 原生 token 流。这两个能力不混为一谈。

### 为什么客户端断开后不取消 Agent 调查？

调查结果属于 Incident 证据，不应因某个浏览器关闭就消失。服务端只停止向已断开的 emitter 发送，后台任务继续完成 run、报告、时间线和审计；用户重新进入后通过 run 详情和事件回放恢复。业务取消使用独立 API，记录取消人、原因和时间，并中断受管任务，因此网络断开和显式取消有清晰不同的语义。

### 事件已经落库，为什么还需要消息队列？

单实例下数据库事件 ID 足以保证顺序、回放和审计。多实例时，请求可能由 A 节点执行而重连落到 B 节点，需要 Redis Streams、Kafka 或数据库轮询来广播新事件。当前没有把单机实现夸大成分布式事件总线，并把多实例协调列为后续演进项。

### 高风险处置为什么禁止发起人自批？

Agent 结论和发起操作可能共享同一个人的判断，独立审批可以降低确认偏差和误操作风险。服务端比较 `requested_by` 与当前审批人，不能只依赖前端隐藏按钮；审批更新还带版本号和待审批状态，避免两名审批人同时覆盖。批准、拒绝都会写入时间线和审计日志。

### 为什么批准后仍不自动执行回滚？

审批闭环和生产执行是两个风险等级。V1.4 先把建议、证据、权限、双人原则和并发控制做实；真正执行还需要凭证隔离、目标环境校验、幂等、回滚验证、超时和执行器审计。当前 `APPROVED` 只表示治理门禁通过，诚实保留这个边界比用模拟按钮宣称自动修复更可靠。

## 可诚实说明的不足

- 当前通知通道是站内记录，未接真实企业微信/短信回执。
- 告警接入是同步 REST，尚未用 Kafka 承担突发流量。
- 数据权限做到角色级，尚未细化到部门和资源范围。
- Runbook 已具备可选 Embedding、持久化向量、RRF、盲化双评分、线性加权 κ、分级 NDCG，以及主库快照写前脱敏与定时保留期擦除，但默认未启用真实 Provider；13 条仍是种子集，隔离 QA 的双评分也不是历史生产标注，未证明真实 Embedding 或 cross-encoder rerank 优于 BM25。当前一致性只支持两名标注人且没有第三方仲裁；快照治理尚未覆盖备份/导出副本、按租户差异化策略和用户级删除请求，当前向量查询为内存全量余弦，不适合大语料；PDF 只支持可提取文本，不做 OCR。
- AI 模式需要外部 DashScope Key，默认演示采用规则引擎。
- 已提供 Prometheus 与 Loki HTTP 适配器，但默认演示关闭外部依赖；当前通过协议级本地 HTTP 契约测试验证，尚未与真实生产集群联调和压测。
- Agent 步骤已经使用持久化实时 SSE 和游标回放；对话仍是完整回答落库后的协议分块，尚未做到模型 Provider 原生 token 流。
- Agent 事件流当前按单实例设计，多实例广播和跨节点任务协调尚未接 Redis Streams 或 Kafka；显式取消只管理当前实例持有的任务。
- 处置审批已完成治理闭环，但尚未接 Argo CD、Ansible、Kubernetes 等生产执行器。
- Postmortem 已覆盖证据快照、独立发布、行动项责任闭环、跨 Incident 待办、逾期事实和 MTTA/MTTM/MTTR；Problem 已覆盖精确指纹复发，但尚未接真实外部提醒/回执、跨 Incident 语义相似/依赖共因聚类、Runbook 命中率趋势和服务 SLO 目标线。
- 已有 MySQL Testcontainers 与四段式 CI 配置；本地是否能运行真实 MySQL 仍取决于 Docker 引擎，托管 runner 结果需以远端 Actions 实际运行记录为准；系统级压力测试也尚未加入。

主动说清边界比虚构“企业级海量并发”更专业。
