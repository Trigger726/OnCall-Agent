# 计划成员权限：实现契约与验证矩阵

状态：CP109 已进入独立 WIP 后端实现与分阶段验证，详见[阶段报告](acceptance/V1.7-checkpoint-109.md)。V39、成员命令/台账/审计和责任入口已有开发实现；实际 MySQL、有数据升级、网络/两 JVM及成员页面未整体验收。以下契约以 CP106 `d0cb78f708b977b6ef79935ad7356eb4f569a517` 的基线分析为起点，不把设计或局部验证写成全部能力。通知/提醒/真实渠道、认领撤销、DST/日历与生产容量继续保留。

## 为什么先做成员关系

当前 `OnCallOpenHandoffService` 和 `OnCallRosterService` 只查 `sys_user` 的 ACTIVE 与全局 ADMIN/OPS_MANAGER/ON_CALL。`OnCallRotationService.member_ids_json` 是轮转顺序，不是计划授权：指定接班、开放认领和手动班次不能据此判断成员。`OnCallController` 管理入口是全局角色门禁，开放详情/覆盖允许审计读取。现有语义是明确的全局运维资格，不应追溯改称已有团队隔离。

[Grafana 的访问模型](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/set-up/manage-access/)区分全局角色、产品权限和团队资源范围；[团队设置](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/set-up/manage-access/teams/)还区分可见性与更新权限。其[代班流程](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/on-call-schedules/shift-swaps-overrides/)通知合格成员、自愿接班和确认。由此得到的本项目设计判断是：先有服务端的计划响应权限，再确定开放请求接收人。下面是 OpsPilot 的独立契约，不声称复制 Grafana 的管理员、RBAC、团队同步或日历语义。

## 权限模型

新增计划/账号关系，不引入多租户或整套组织团队系统。响应与管理是两项独立权限；管理权限不代表自愿承担班次。全局账号仍须当前有效，JWT 中旧角色不是权威。

| 操作 | 拟定服务端条件 |
| --- | --- |
| 读取既有 roster/current/coverage、开放历史 | 保持当前认证与审计读取契约；此阶段不是私有计划读隔离 |
| 新建成员、变更/撤销成员权限 | 当前 ACTIVE ADMIN，或当前 ACTIVE OPS_MANAGER 且该计划有管理权限；不能用其他计划授权 |
| 创建/取消班次、管理轮转、管理撤销 | 同上；新分配目标另须该计划的响应权限与活跃运维资格 |
| 发布开放请求、发起指定接班/双向互换 | 本人对应计划的响应权限，源有效且本人所有；原业务版本、时段等约束不变 |
| 新认领/接受指定接班或互换 | 每个新责任对应计划的响应权限；源负责人也须满足该请求的新责任资格；管理角色不能代同事接受 |
| 本人撤回未认领请求或拒绝指定请求 | 保留当前本人/global 资格条件；即使已离开计划，也允许安全结束自己的未接受意图，不新建责任 |
| 原键、原内容求已提交回执 | 当前账号/global 资格仍有效且是原操作人；允许成员已撤销后的只读确认，不新建或复活覆盖 |
| 后台续排 | 对每个目标再查该计划响应权限；不可因为某人失权跳过其轮次换人；已有 GENERATED 事实不重写 |
| 将来的开放请求广播/提醒 | 发送阶段再查对应计划响应权限、账号资格与请求仍可接受；不是所有全局运维用户 |

ADMIN 的全局管理能力为本项目明确的恢复入口；ADMIN 若要自己认领仍需响应成员关系。OPS_MANAGER 不因全局职位自动管理或响应所有新计划。ON_CALL、AUDITOR 不能仅凭成员行获得管理权限；授予管理位时须校验目标当前为 ADMIN/OPS_MANAGER。

读取边界必须诚实：此阶段保留 auditor 的历史覆盖 200，并保留既有全局可观测查询。未来私有计划可见性需独立设计，不能用写权限通过宣称整个系统完成资源读隔离。成员管理查询可返回该计划的成员与当前有效性，不能把全局用户下拉当成员清单。

## 数据与有数据升级

WIP 新增 V39；已验收分支仍停留 V38。不得修改 V1–V38 或 JDBC 迁移的已发布校验和。

- 成员行拟用 `(schedule_id,user_id)` 主键/外键，`active,can_respond,can_manage,version,created_at,updated_at,origin`。撤销只标记 inactive、递增版本，不删除原行或责任。版本不得溢出；缺失行的首次授权需要显式 `expectedVersion=null`（表示预期不存在），HTTP 必须区分缺失字段与显式 null，不把遗漏等价于第一次授权。
- 管理命令固定 `userId,expectedVersion,active,canRespond,canManage,operationKey,reason`，规范 UUID、说明 1–500 字。独立操作台账按 actor/key 唯一，保存计划/目标/完整捕获命令/提交版本与时间；同键异内容 409，旧版本 409，无隐式重基。首次授权时不能伪造已有版本；重新激活使用实际保留行版本。
- 成员行、操作台账与审计同事务。审计记录实际认证 actor/IP、旧/新权限与说明；事后审计失败必须回滚全部行，不只返回错误。
- 兼容策略是一次性显式回填：升级时已有计划 × 当时 ACTIVE 运维用户，回填响应权限，已有 ADMIN/OPS_MANAGER 同时回填管理权限，`origin=MIGRATED_GLOBAL_V38`。这保存切换前的全局写能力，不伪称历史原本有团队隔离。inactive/auditor 不回填。旧班次/轮转顺序/接班/互换/认领回执不变。
- 后续新账号、新计划均不自动加入，不按角色动态补授权。停用后恢复账号不能复活已撤销成员行。旧成员在其他新计划不自动有权。回填的权限需要管理员按真实团队范围收敛，演示和部署说明必须显示其来源。
- 验证真实非空 V38 → V39 升级：旧 JAR 产生 OPEN、CLAIMED、WITHDRAWN 请求及取消覆盖/原认领回执，再迁移并重启；原业务全行摘要、38 个版本校验和、责任/取消事实不变，回填准确且不重复。不能只测新建空库。

现 `verify-oncall-open-handoff-http-ci.cjs` 明确断言最高 V38，真实 MySQL 升级门禁是 V37 → V38。落地 V39 时必须更新显式当前版本断言，同时保留旧 10 流程和所有原 case-ID，并新增独立非空 V38 → V39 门禁。不能仅删除最高版本检查、动态接受任意最大版本或用旧绿灯替代新迁移验收。

## 锁与撤销边界

所有业务先锁计划；涉及两计划时按计划 ID 升序，再按既有业务顺序锁请求/轮转，相关账号按 ID 升序。成员管理也先锁计划，随后按账号 ID 升序锁 actor/target；计划锁串行化成员行首次插入、更新与新责任提交，禁止先锁账号再去等计划。跨计划同 actor/key 用账号锁协调并检索全局操作台账，不能只靠单 JVM synchronized。

新责任在锁后查最新成员/global 角色，不依赖前端候选清单或早期事务快照。成员撤销与认领争抢允许：认领先提交后撤销则责任保留；撤销先提交则新认领 403 且请求/覆盖/回执/审计 0 变化。需要实际独立事务屏障验证两种顺序，不靠固定 sleep。

撤销响应权限不是取消既有班次。当前覆盖、历史认领、已提交原回执不重写；已有 GENERATED 轮转行不删除或偷偷换人。需要结束现有责任时另走已有明确版本/说明/审计的取消流程，并核对缺口；不能通过删成员自动解除责任。无权限的 OPEN 发布人可撤回自己的请求，但他失去响应权限后其他人不能再据此创建新责任。

`OnCallRosterService.create` 是手动管理、后台续排、指定接班和开放认领的共用写入口：目标资格要统一约束，但不能在里面强制所有调用都是管理角色，从而把合法的 ON_CALL 自愿接受流程拒绝。各入口分别检查发起操作权限，共用写入口检查目标响应权限；后台扫描不能把 `actor=null` 当任何外部 API 的授权旁路。
