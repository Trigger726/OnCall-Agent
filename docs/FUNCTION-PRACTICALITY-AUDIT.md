# 功能实用性审查与落地边界

2026-10-26，基线 `130a860`。范围为当前 11 个登录后页面、登录流程及其对用户开放的二级业务能力；不是隐藏后台所有类的逐方法审计。先按一个小型自建值班团队判断，等待真实团队规模/使用信息校正。**没有生产使用埋点或真实客户日志，以下频率都是工作流假设，不是使用率统计；演示数据库里的点击和记录不能证明高频。**

## 取舍规则

保留的功能必须说清：操作者、触发条件、输入来源、可完成的动作与验收结果。高频入口服务每班“发现告警—定位事件—找负责人/查证据—恢复验证”；事件结束后再复盘。低频但高风险的权限、审批、取消、审计不按点击率删除。只演示固定数据、无法泛化、误导实际能力或重复触发同一动作的 UI 直接删。工程评测保留在维护流程，不当日常业务仪表盘。

此规则与 [Google SRE 的可行动告警、责任协调与控制](https://sre.google/resources/practices-and-processes/incident-management-guide/)及 [PagerDuty 的事后复盘/防复发行动](https://docs.pagerduty.com/ops-guides/incident-response-guide/after-an-incident)相符；具体删留仍来自本项目源码，不用这些资料证明本项目真实使用率。

## 全部页面与二级能力

频率：“每班/故障时/每周/配置变更时”均为预期；“条件保留”表示先具备对应依赖，否则不能把演示成功当可上线。

| 能力 | 谁在何时使用、实际完成的事 | 依赖与现实边界 | 处理 |
|---|---|---|---|
| 运行总览：活跃事件/P1/触发告警/异常资源 | 值班人每班掌握待处理积压，再进入事件 | 读取实际数据库；不是自动发现所有基础设施 | 保留 |
| 首页平均确认时间卡 | 只有全历史平均、无样本数/窗口；无样本后端返回 0 | 容易把未知看成达标；运营分析已有严谨指标 | 删除重复展示 |
| 首页事件/当前值班/风险资源跳转 | 值班人直接找到事件和责任人 | 需真实告警、有效排班、资源权属 | 保留 |
| 首页趋势图 | 值班人观察事件记录变化 | 实际只是有记录的最近日期，不是实时监控 | 条件保留，不扩大口径 |
| 告警列表/状态与等级筛选/事件跳转 | 每班排查触发信号、压缩次数、关联事件 | 必须有监控平台投递 | 保留 |
| 页面“接入告警”手填测试器 | 没有生产流程；资源四选项、prod-east 标签写死 | 实际为演示注入，不是配置监控接入 | 删除表单、按钮、提交逻辑 |
| Alertmanager 真实接入/拒绝台账/重放 | 集成运维在投递失败、资源未映射时修复与重投 | 需独立 Secret、资源映射；不能无意义循环重放 | 保留；异常时使用，不删失败恢复 |
| Incident 搜索/稳定分页/真实总数 | 每班按编号/服务定位当前或历史事件 | 后端字面搜索；不是全文引擎或大规模性能承诺 | 保留 |
| Incident 接手/调查/缓解/恢复/关闭 | 每次故障，显式推进处置责任和状态 | 当前权限和版本校验必须保留 | 保留 |
| 事件时间线/人工记录 | 处置人记录证据与进展，方便交接复盘 | 人工记录不是自动执行日志 | 保留 |
| 一键 Agent 调查与步骤/证据 | 故障时收集已有事件/资源/变更/指标资料 | 依赖实际数据；无数据不能自动得出根因 | 条件保留 |
| 排队/取消/超时/幂等/流恢复 | 调查中断、误发、服务过载时保证可控制 | 属于安全运行机制，不靠“低频”删除 | 保留 |
| 重复“运行第一次/重新生成报告”按钮 | 和页头同一个 investigate 动作 | 没有独立任务，空卡只占空间 | 删除重复入口 |
| 报告、提案、复盘的空占位 | 无证据/未恢复时无法产生有效动作 | “暂无”多卡不等于业务能力 | 去掉无动作空卡；有数据/可操作时仍显示 |
| 高风险提案独立审批 | 相关变更引发故障、需受控回滚建议时复核 | 批准只解除治理门禁；没有生产回滚执行器 | 保留审批，禁止宣称已自动回滚 |
| 事故复盘/独立发布 | 恢复后梳理影响、根因与教训 | 未恢复不提前编造结论；发布需独立复核 | 保留，仅到达条件时显示 |
| 防复发行动项/负责人确认/期限 | 事故后每周跟踪是否真正有人处理 | HTTP 投递成功不等于负责人接手或已完成 | 保留 |
| OnCall 对话/多会话/复制导出 | 故障时整理证据、问手册、继续同一事件 | 默认规则检索；云模型是可选依赖 | 保留 |
| 回答精确引用/旧版本警示/ACL | 执行建议前核对原出处 | 不能用最新版替换历史来源或绕过权限 | 保留 |
| 模型与 API 部署说明 | 管理员首次配置、故障排查时查看 | 只说明变量/文件和重启，不在线存 Key | 保留但非日常主流程 |
| 当前值班/值班表/覆盖检查 | 每班找人；排班变更后检查缺口 | 需要真实成员、时区与有效时间段 | 保留 |
| 成员资格与授权 | 人员入离组、计划调整时 | 决定是否有权排班/接班；不是多租户隔离已完成 | 保留安全边界 |
| 轮转规则/指定交接/调班 | 每周排班、临时请假时调整责任 | 小团队不一定天天用，但有明确任务 | 条件保留 |
| 开放接班认领 | 原值班人临时无法履职时寻找接班人 | 必须有合格候选与明确接受者；不能把发布当交接完成 | 条件保留，不作为强制流程 |
| 升级策略与扫描 | 未确认事件超时后寻找更高责任人 | 当前站内路由，不自动等同短信/电话到达 | 保留并修正文案 |
| 外部通知回执/人工重投/管理员队列 | 集成运维处理真实通知失败、积压时 | 默认关闭；需真实回调、接收人映射和确认流程 | 条件保留、管理维护使用 |
| 手册查找/已发布文档/导入修订 | 故障时查步骤；规则变更时维护知识 | 内容要有负责人、适用服务、验证方式 | 保留 |
| 手册独立发布与角色可见性 | 新版处置步骤入库时防误发 | 删除会放大错误操作风险 | 保留在知识维护 |
| 原 contains/BM25/RRF 对比展示 | 解释项目演进，不是值班任务 | 还含固定 3/13 文本说明；离线分数非线上成功率 | 删除产品展示，历史报告/测试保留 |
| 默认 Redis 示例搜索 | 打开页面即替用户保存一次演示查询 | 不是用户真正的信息需求 | 删除自动示例查询 |
| 索引重建、模式对比、离线评测/历史 | 管理员改语料/算法或升级后回归 | 无需每次打开手册都加载 | 保留，主动打开“知识维护”才读取 |
| 相关性反馈/独立复核/一致性 | 使用者发现错误结果，维护者周期复核 | 不用单人标签直接宣称生产质量 | 反馈保留；复核/统计移维护 |
| 检索趋势/快照留存/清理 | 维护者排查检索退化或执行留存策略 | 留存清理是安全管理，不是值班人每天操作 | 保留，按需读取 |
| 资源负责人/环境/已登记依赖/近期变更 | 故障时找归属与关联变更 | 当前是只读台账，不是实时发现/自动同步系统 | 保留；上线前补真实维护来源 |

| 严谨 MTTA/MTTM/MTTR 与服务拆分 | 负责人每周找响应瓶颈 | 明确窗口/样本/里程碑；不能据 Demo 推生产改善 | 保留运营分析，不放首页重复指标 |
| SLO 与错误预算/告警规则导出 | 服务负责人按周检查目标与燃尽 | 必须接 Prometheus 好/总事件计数；没有数据为未知 | 条件保留，不能拿 Incident 数代算 |
| 重复事故/Problem/已知错误/长期修复 | 同类事故反复发生后，负责人消除复发 | 精确指纹匹配不是已测“高精度” | 保留，去掉无证据精度宣传 |
| 审计日志 | 审批/安全检查/争议追溯时 | ADMIN/AUDITOR/OPS_MANAGER；不以低频为由删除 | 保留 |
| 本人改密/撤销会话 | 人员安全管理、凭证风险发生时 | 必须可达并保留当前授权检查 | 保留 |
| 登录自动填演示管理员和密码 | 只方便 Demo，正式使用没有任务价值 | 默认特权身份/演示密码容易造成误用 | 删除自动填充；不删除演示数据库账号 |
| 浅深主题/MiSans/流光 | 用户已明确指定的阅读与视觉偏好 | 尊重减少动态/无 GPU 降级，不把装饰算业务能力 | 按既定要求保留 |

## 实际落地：先能跑完一条闭环

试点只需：一个真实服务及负责人、一条带稳定资源编码的监控告警、一份经过审核的处置手册、一个有效值班计划、处理人与另一名复核人。验收必须实际经过“真实告警进入→找到责任人→事件确认与证据记录→恢复验证→复盘/行动项→另一人复核”，再讨论是否需要 SLO、开放接班、语义索引等扩展。不能用手工制造几条 Demo 数据来替代这些接入条件。

上线阻断项（本次识别，不伪称已修复）：

1. **兼容 `/api/v1/alerts/intake` 仍被 SecurityConfig 允许匿名写入**。本次删的是页面测试器，不是所有业务摄取 API。上线前需给该兼容接口补认证/来源控制或在入口网关封禁；正式监控走独立 Secret 的 Alertmanager 接口。当前演示仅回环地址，不可直接公网暴露后端。
2. CMDB 当前只有读 API；真实资源的持续登记/更新流程仍缺失。必须确定受控导入/同步来源与负责人，不能靠长期手改种子 SQL 当运维流程。
3. 部署前替换默认 JWT、演示账户密码与数据库口令，采用真实 Secret 注入、备份与恢复检查；本次没有删除/改写已有账户或用户数据库。
4. 站内路由、HTTP 技术回执、人已接受/实际恢复分别验收。未连接真实渠道时不承诺电话/短信送达；未接部署平台时不承诺自动回滚。
5. 先用真实试点记录“每项功能解决了什么任务、失败如何恢复”，再决定二次删减。需要真实使用观测才能断言哪个业务功能确实无人用；不添加伪造频率或按访问量删安全能力。
