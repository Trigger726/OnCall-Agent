## 为什么下一阶段做这个

原始 `archive/oncall-original-2026-08-19` 保留的是 SuperBizAgent 的 RAG/Agent、告警、日志和工具链，没有持久化排班认领事务。现 OpsPilot 的 `OnCallHandoffService` 必须指定 `targetUserId`，V27 的目标用户也非空；`OnCallSwapService` 是指定双方的两段互换。缺口是原负责人发布需求后，合格成员自行承担责任，而不是管理员替别人点击同意。

参考 [Grafana 代班请求与临时覆盖](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/on-call-schedules/shift-swaps-overrides/)：不知道谁有空时发布请求，由成员自愿承担；指定临时覆盖则是已与特定同事协调的另一流程。[PagerDuty 开放排班](https://docs.pagerduty.com/incident-management/schedules/edit-shift-based-schedules)允许未分配轮转由响应人员自行选择。两者机制不同，不能把厂商全部团队权限、通知、日历能力冒称本项目实现。

## 产品语义与兼容边界

首先实现**本人已有普通班次的开放接班请求**，不是无负责人排班，也不是两个时段互换。原班次保持不变；成功认领生成独立临时覆盖，当前实际责任仍由 coverage 查询判定。

发布和认领均需本人当前活跃运维资格；不能认领自己发布的请求，管理角色不能代另一个人认领。现项目尚无计划成员关系，第一阶段沿用明确的全局 ADMIN/OPS_MANAGER/ON_CALL 资格，不伪称团队成员 ACL。若引入计划成员表，必须补迁移、历史兼容和真实授权测试，不能只在前端过滤。

发布允许包含于本人有效普通班次的整秒子时段。尚未结束且源仍有效时可认领正在进行的请求，只覆盖数据库当前时间向上取整后的剩余部分；原请求时间不改写。结束、源取消/版本变化、计划停用或其他覆盖冲突时不创建覆盖。拒绝新责任和已提交原意图求回执是两种操作，不能混淆。

## 后台实现约束

- 新的独立表与服务，不将 V27/V34 的指定参与者改成 nullable，也不修改已发布 Flyway checksum。状态为 OPEN/CLAIMED/WITHDRAWN；过期是查询事实，不凭浏览器时钟伪造新状态。
- 明确版本、规范 UUID 和有界说明；所有 HTTP 版本字段必须 `@NotNull`，缺失版本不能等价于 0。发布键按申请账号隔离；认领操作键按实际认领账号隔离。原键与原内容重复只读取既有事实，变内容或跨请求复用必须冲突。
- 事务锁顺序遵循现有计划锁 → 请求锁 → 参与者账号 ID 升序，采用最新数据库资格和锁后时间。不依赖单进程内存锁；不同计划同账号的键也必须协调。
- 认领、创建覆盖、认领回执台账和审计在同一事务。两人争抢只允许一人创建一条覆盖；后续审计失败时全部回滚，不能留下 CLAIMED 或半提交覆盖。
- 原认领回执需要重新检查当前认领人资格；覆盖取消后原键回执不能重新创建覆盖。不自动重基捕获版本、不把另一个账号的成功认领当成本人回执。
- 列表在 SQL 中先按请求/计划/状态/当前账号过滤后再限制 201，返回最多 200 与 truncated；AVAILABLE 不能因前 200 条无关请求隐藏真实可认领项。数据库快照、历史认领、覆盖取消与实际责任分别展示。
